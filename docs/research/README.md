# 调研与复用决策记录（docs/research）

本目录存放**联网调研与复用决策**的正式记录：这次打算沿用或引入某项技术时，查了什么、看到什么、为什么沿用或放弃。记录随代码一起进仓库，供作者自检、监工复核和后续接手者复用。

- 位置固定在仓库内 `docs/research/`，不放 `.pg17` 等仓外目录。
- 一条记录一个文件，命名 `YYYY-MM-DD-<主题>.md`。
- 只记**当前把握**：版本、来源、决定。⛔ 不补写「某历史片当时查过什么」——没有当时记录就不补，禁止事后伪造检索日期、检索词和来源。

## 1 什么时候必须写

自 R10 起，**每一片交付都要带一条记录**，包括看起来「不需要调研」的片：

| 片子类型 | 记录要求 |
| --- | --- |
| 引入新依赖、新运行时、新工具链 | 完整记录：每项技术一套字段（见 §3） |
| 沿用现有技术栈、只改代码 | 栈基线记录（本目录 `stack-reuse-decision` 那条）＋本片是否有偏离 |
| 纯内部工具、文案、测试、脚本 | 最短记录（见 §7）：检索日期＋检索方式＋来源版本或提交＋≥2 来源＋决定＋理由 |

不做记录的例外只有一个：本片既没有引入依赖，也没有采用任何新做法，而且不涉及任何版本判断——即便如此也建议留 5 行最短记录，成本低于事后解释。

三档记录都受 `node tools/verify-research-records.mjs` 机械校验：它是 `npm run test:docs` 的第二段，CI 的 `Development documentation` workflow 也跑同一条命令。校验只认能机械判的部分——文件名与日期、记录级四项、按项来源条数、技术七项齐不齐；「决定」是否真被证据支撑仍靠复核。

## 2 命名与文件

- 文件名：`YYYY-MM-DD-<主题>.md`，日期是**实际检索那一天**的本地日期，不是提交日期、不是排期日期。
- 主题用短词、小写、连字符分隔，例如 `stack-reuse-decision`、`miniprogram-base-library`。
- 同一主题的续篇新建当天日期文件，旧文件保留不动，不覆盖、不改名；历史文件是当时的证据。
- 栈基线文件名中的主题固定为 `stack-reuse-decision`，每次全量复核都新建一个当天日期的文件。

## 3 必带字段（每项技术一套）

| 字段 | 含义 | 填写要求 |
| --- | --- | --- |
| 现用版本 | 仓库里正在跑的版本 | 必须写清取自哪个文件或哪条命令，命令要能直接复现出该读数 |
| 上游维护状态 | 官方支持阶段与期限 | Active LTS／Maintenance／EOL 日期，附来源；查不到就写「未取得」 |
| 可复用部分 | 本项目里哪一层／哪个目录／哪条脚本复用了它，复用面多大 | 必须写到可核的路径、脚本名与数量，并给出计数命令；确无可复用面时用命令输出作证据，⛔ 不写「无」「不适用」这类空话 |
| 许可证与署名 | 许可证名与署名、声明要求 | 以官方许可页或包元数据为准，不凭记忆填 |
| 兼容性 | 与仓库现状的交叉点 | Node 版本、ESM、目标运行时、小程序基础库、数据库大版本等 |
| 引入成本 | 体积、运行时依赖数、构建时长 | 允许写「未实测」，但该字段不得省略 |
| 决定 | 沿用／待升级／不引入／自研 | 必须带理由，只写结论不算记录 |

记录级另四项与上表合起来是裁定的十项必填字段：**检索日期**、**检索方式／检索词原文**、**≥2 条本轮抓取的来源 URL**（见 §4 与各节「检索来源」）、**来源版本或提交**（写在「现用版本（证据命令）」里，含版本号、提交或 tag SHA；也可以单起一行 `- 来源版本或提交：…`）。写成单独一行时，值必须是 `x.y.z` 形式的版本号、40 位提交 SHA，或 `commit`／`sha`／`tag` 字样后紧跟的 7–40 位十六进制；裸的短十六进制数字（例如 `1048576`）只是读数，不算版本证据。

## 4 检索留痕的最低要求

- **检索日期**：本地日期 `YYYY-MM-DD`。
- **检索词原文**：逐字抄实际输入的检索串；如果是直接打开已知官方页，就写「直接抓取官方页，未使用检索词」，不要编一个检索词。
- **来源 URL**：每项 ≥2 条，且必须是**本轮实际抓取**的页面；同一域名要区分是两个不同页面，同一页面的转载不算第二条。这里的「每项」是**每一项技术**：完整记录按技术段逐项核（含该段的「检索来源」子表），最短记录按整条记录核（§7：一篇只讲一件事）。⛔ 不认「全篇一共几条」这种凑数——一项独占四条、另三项零条，仍然不合格。
- **按页面去重**：去掉 `#锚点` 与 URL 尾部斜杠、域名与路径大小写归一后相同就是同一页；同一页的两个锚点只算一条来源。
- **哪些表按行核**：只有「检索来源」表（表头含 来源／URL／链接／读数／证据，或挂在 `### …来源…` 子标题下）才按行核每项 ≥2；带「技术」列的总览表、证据总表只是列清单，不参与按行来源计数。
- **只认正文**：围栏代码块（``` / ~~~）里和 `<!-- -->` 注释里写的字段、来源、版本一律不算数——证据要留在正文里，注释是草稿区。
- **抓到的读数**：页面显示的 latest 版本、EOL 日期、许可证名等，写给后续复核的人看。

## 5 取不到怎么办

- 写「未取得」，并写原因（工具不可用／页面需登录／页面无法渲染／该项检索未执行）与已试过的 URL。
- ⛔ 不得用记忆、二手转述或「据我了解」替代抓取；不得把未取得的项按「已确认」写入结论。
- 未取得项必须同时进交接的「未取得项」清单，让下游知道哪里没有证据。

## 6 空模板（可直接复制）

一项技术一段；字段统一写成 `- 字段：值`（冒号），**不要**用表格——表格只留给「检索来源」。来源表按技术分行：一行就是一项技术，该行至少 2 条 URL；同项的两个页面要真的不同（不同站点或不同路径），同一页面的两个锚点不算两条。

```markdown
# YYYY-MM-DD <主题>

- 检索日期：YYYY-MM-DD
- 检索方式：检索词「……」／直接抓取官方页（未使用检索词）
- 来源版本或提交：<x.y.z 版本号，或 40 位 SHA，或 commit／tag 后跟短 SHA>
- 一句话结论：……

## 1 <技术名>

- 现用版本（证据命令）：`命令` ⇒ 读数
- 上游维护状态：……（来源 1、来源 2）
- 可复用部分：……（复用的目录／脚本与数量；计数命令 ⇒ 读数）
- 许可证与署名：……
- 兼容性：……
- 引入成本：……（未实测）
- 决定：沿用／待升级；理由：……

### 检索来源

| # | URL | 本轮读数 |
| --- | --- | --- |
| 1 | https://…… | …… |
| 2 | https://…… | …… |
```

## 7 最短记录范例（内部工具片）

最短记录一篇只讲一件事（一项技术／一个决定）：来源条数按**整条记录**核，一篇里塞两件事就会摊薄成每件一条，反而过不了门禁。要写多项技术，用 §3／§6 的完整记录。

```markdown
# 2026-10-18 内部脚本：日期格式化是否引入依赖

- 检索日期：2026-10-18
- 检索方式：直接抓取 npm 包元数据，未使用检索词
- 来源版本或提交：dayjs 1.11.13（`registry.npmjs.org/dayjs/latest` 的 `version` 字段）
- 来源：https://registry.npmjs.org/dayjs/latest（版本、许可证）；https://registry.npmjs.org/dayjs（发布时间与维护者）
- 决定：不引入。理由：仅 1 处格式化，Node 24 内置 Intl 足够；新增依赖会扩大锁文件与供应链面。
```

最短记录也要有真实来源；讨论和口头结论不进仓库。

## 8 与门禁的关系

- 本目录新增或修改文档必须过 `npm run test:docs`：表格同一块内列数一致、相对链接目标存在、无替换字符（U+FFFD）。
- `npm run test:docs` 的第二段是 `node tools/verify-research-records.mjs`：命名、记录级四项、按项来源、技术七项、legacy 白名单都在这里机械判；CI 的 `.github/workflows/development-docs.yml` 在同一条链上跑它。手动自检用 `node tools/verify-research-records.mjs`（仓根）或带一个目录参数。
- 记录中的版本读数必须与仓库现状对得上：写清文件路径与命令，复核者按命令就能复现。
- 记录是**决策证据**，不是能力声明；「沿用」不等于该技术在本仓库已通过全部验收。
