# 耕云 · 发版 runbook（2026-10-22）

- **适用版本**：`services/api/db/migrations` `0001..0027`（27 个迁移、26 个 down）、PostgreSQL 17.11、容器镜像 `node:24.16.0`。
- **依据基线**：`origin/main = 56ed9f2cf89494a8bb02e03830a134cb8a0e2af`。
- **本页是什么**：**一次发版**的端到端操作清单——门禁 → 备份 → 迁移 → 启动 → 验证 → 灰度 → 回滚 → 值班。每一步都给出**按标注 shell 直接执行**的命令（`bash` 段贴进 bash、`powershell` 段贴进 PowerShell）、期望输出、失败处置。
- **本页的「可复制」到哪为止**：命令里没有等你回填的空位；但**需要环境输入的地方**（部署基址 `GY_DEPLOY_BASE_URL`，见 §4.2）由你显式提供，脚本先校验、不合法就 `exit 2`。本页不给默认域名，也不承诺「不填任何东西就能跑通」。
- **本页不是什么**：不是首次装库/建库手册（那是 `deploy/postgres-cvm/runbook.md` 与 `deploy/postgres-cvm/provision-db.sh`），不是验收结论（本页不代表任何环境已验收）。
- **命令面的来源**：全部来自仓库既有脚本（`deploy/postgres-cvm/*.sh`、`tools/verify-release-materials.mjs`、`npm run`）。本页不发明新脚本、不改产品代码。
- **已真跑的范围**：§9 的备份/删库/恢复读数于 2026-10-22 在本机原生 PG 17.11（端口 55728）实测；CVM 与云托管侧**未取得**（见 §10）。

> ⚠️ **命令分两栏读**：带 `cvm` 标记的在目标 CVM（Linux，`runuser -u postgres`，socket 走 `/var/run/postgresql`）上执行；带 `local` 标记的在本机 Windows 演练环境执行。两套命令**判据相同、路径不同**，不要把本机路径粘到 CVM。

## 0 适用范围与前置

发版单位是「一次数据库变更 + 一次应用版本切换」。开始前必须已具备：

| 前置件 | 判据 | 没有就不许开始，因为 |
| --- | --- | --- |
| 可用的 PG 17 实例 | `psql -c "select version()"` 返回 `17.` | 备份/恢复与迁移都依赖主版本一致 |
| 业务库 `gengyun` 与两个登录角色 | `gengyun_cvm_owner`（属主/迁移）、`gengyun_api_runtime`（运行时，最小权限） | 迁移用属主、应用用运行时，混用会把最小权限判据打死 |
| 备份目录在持久存储上 | `GENGYUN_BACKUP_DIR` 默认 `/data/gengyun/backup`，非临时盘 | 回滚依赖它，放在临时盘等于没有 |
| 本页 §9 的恢复演练读数 | 最近一次演练 `PASS` 且 dump 的 sha256 与本次发版备份可复现 | 「脚本存在」不等于「备份可恢复」 |

**硬性约束**：迁移只向前（`migrate.ts` 的命令闭集是 `up | status | list`，**没有 down**）；回滚数据库只能手工执行 `migrations/rollback/` 下的 down 脚本（见 §7.4）。这个约束决定了「迁移失败」的处置与「应用回滚」不同——先把这条记住再往下走。

**开工前确认三件事的读数**（任一读不出就不发版）：

```bash
# cvm：确认库、角色、迁移账本三者都在
sudo -u postgres psql -h /var/run/postgresql -d gengyun -tAc "select current_database(), (select count(*) from schema_migrations)"
sudo -u postgres psql -h /var/run/postgresql -d postgres -tAc "select rolname from pg_roles where rolname like 'gengyun%' order by 1"
sudo -u postgres psql -h /var/run/postgresql -d gengyun -tAc "select count(*) from information_schema.tables where table_type='BASE TABLE' and table_schema not in ('pg_catalog','information_schema')"
```

期望输出（本机演练库实测值，CVM 上表数应一致）：

```text
gengyun|27
gengyun_api_runtime
gengyun_cvm_owner
74
```

**失败时怎么办**：`current_database()` 报库不存在 ⇒ 库还没建，回到 `provision-db.sh`，本轮发版取消；角色列表不足 2 行 ⇒ 先跑 `deploy/postgres-cvm/sql/20-login-roles.sql`；表数不是 74 ⇒ 迁移没跑全或跑到了半途，按 §3.3 的账本核对后再决定，**不要**直接 `up` 掩盖。

## 1 发版前检查

### 1.1 材料门禁（离线，30 秒）

**这一段跑在 bash 里**（本机 Git/MSYS bash，或 CVM 的 bash）。先说清门禁怎么找 bash：工具内部是 `execFileSync('bash', …)`，**从 PATH 解析**，它不读 `GY_BASH`——本机 PATH 上的 `bash` 若落到 WSL 存根，必须先把真 bash 的目录前置进 PATH，否则门禁照旧用错 bash：

```bash
# bash（local / cvm）：把真 bash 目录前置（按你本机实际位置改；已能直接跑 bash 时前两行可省）
export PATH="/d/Git/bin:$PATH"
bash --version | head -1
node tools/verify-release-materials.mjs
echo "exit=$?"
```

**只在 PowerShell 里操作时**用下面这段同义命令（两块命令**别混抄**：`$env:` 是 PowerShell 语法，贴进 bash 只会被当成普通字符串赋值，门禁仍然用错 bash）：

```powershell
# powershell（Windows PowerShell 5.1）：同一个门禁，语法换成 PowerShell
$env:PATH = 'D:\Git\bin;' + $env:PATH
node tools/verify-release-materials.mjs
echo "exit=$LASTEXITCODE"
```

期望输出：

```text
16/16 项通过（离线文档核验；不代表部署、云端或运行期已验收）
exit=0
```

**失败时怎么办**：门禁逐条打 `PASS`/`FAIL`，`FAIL` 行自带原因与定位。只有两类处置：① 材料问题（索引缺行、runbook 缺节/有占位符、脚本语法）⇒ 修材料，**不要**改判据绕过；② 环境问题（`bash` 解析到 WSL 存根，报 `wsl: 检测到 localhost 代理配置`）⇒ 按 §1.1 把真 bash 前置进 `PATH` 后重跑（`GY_BASH` 只被 `npm run test:unit` 那条链上的 `tests/unit/bash-resolver.mjs` 读取，对本条门禁无效），仍红则按材料问题处理。

### 1.2 迁移与 down 配对

```bash
# 迁移数必须比 down 数多 1（0001 无 down）；差值不是 1 说明有人只加了一半
ls services/api/db/migrations/[0-9]*.sql | wc -l
ls services/api/db/migrations/rollback/*.down.sql | wc -l
```

期望输出：

```text
27
26
```

**失败时怎么办**：27/26 是 2026-10-22 的基线。数字变了不算错，但**必须同时**改本页 §1.2、§3.2、§5.4 的读数并提交，否则下一个执行者会拿旧读数判断「迁移没跑全」。差值为 2 以上 ⇒ 回滚路径缺脚本，本次发版**不予批准**（迁移没有 down 就无法回滚）。

### 1.3 记录发版前容量基线

发版判据里 R2 是「p95 不超过发版前基线的 2 倍」，所以基线必须在切换前取，切换后取不到。

```bash
# local：串行取样 200 条，取 p95（工具与口径见 docs/verification/gy-i23-latency-capacity-local-20261020.md）
for i in $(seq 1 200); do curl -s -o /dev/null -w '%{time_total}\n' "http://127.0.0.1:3310/api/v1/knowledge?limit=20"; done | sort -n | awk '{a[NR]=$1} END {printf "p95=%.3f ms n=%d\n", a[int(NR*0.95)]*1000, NR}'
```

期望输出（本机回环基线，2026-10-20 实测 p95 12.6 ms；阈值取 2 倍即 25 ms）：

```text
p95=12.559 ms n=200
```

**失败时怎么办**：读不出数（服务没起、端口不对）⇒ 先修探活，不带基线不发版；读数比基线高一倍以上 ⇒ 不是发版问题而是环境问题（同机有其他负载、连接池被打满），换一台干净的测量机重测，**不要**用坏基线去放松后面的判据。

## 2 发版备份

### 2.1 执行一次逻辑备份

```bash
# cvm：仓库既有备份脚本，产出 pg_dump -Fc + 清单 + 保留期
sudo GENGYUN_BACKUP_DIR=/data/gengyun/backup GENGYUN_DB_NAME=gengyun \
  /opt/gengyun/deploy/postgres-cvm/backup-postgres.sh
echo "exit=$?"
```

期望输出（判据是**退出码与末段路径**，不是固定文案）：

```text
exit=0
```

同时 stdout 末段必须给出这次产出的 dump 路径（形如 `gengyun-20261022T063219Z.dump`）与同名清单文件路径。退出码语义由脚本约定：`0` = dump 已产出**且** `pg_restore --list` 能读出目录；`1` = 备份失败（`pg_dump` 报错、产出为空、集群未就绪、缺 `pg_dump`）；本脚本不产生 `2`。

**失败时怎么办**：`exit=1` 时先在 dump 目录看有没有**零字节**残留（有就删掉，避免被误当可用备份）；再确认集群就绪（§0 的三条命令）；`磁盘满` 出现在 stderr ⇒ 清理保留期外的旧备份（`backup-postgres.sh --dry-retention` 先看会删什么，再实跑）后重试。**⛔ 不要带着 `exit=1` 继续发版**：这次发版就没有可回滚的备份。

### 2.2 校验 dump 可读并记账

```bash
# cvm：把 dump 的可读性与指纹记下来，后面 §7 回滚要用它
DUMP=/data/gengyun/backup/gengyun-20261022T063219Z.dump
sudo -u postgres /usr/pgsql-17/bin/pg_restore --list "$DUMP" | grep -c ';'
sudo sha256sum "$DUMP"
```

期望输出（TOC 条目数随表数增长；本机 74 表/8 视图的演练库为 833）：

```text
833
b110f47d8a55d7de37518bf40dd727a1e199fede44acb907ed31faf6a02f901d  /data/gengyun/backup/gengyun-20261022T063219Z.dump
```

**失败时怎么办**：`pg_restore --list` 报 `could not read` ⇒ dump 损坏，回到 2.1 重做（并把损坏文件改名保留，别删，它是唯一线索）；条目数比上一个成功备份少一半以上 ⇒ dump 被截断，同样重做。

### 2.3 恢复演练（每次发版必做，15 分钟内）

「备份成功」和「备份可恢复」是两件事，脚本自己也在注释里这么写。这一节就是把它变成一件事。

```bash
# cvm：在隔离库上恢复，五条判据全 PASS 才算有可回滚的备份
sudo /opt/gengyun/deploy/postgres-cvm/restore-drill.sh \
  --dump /data/gengyun/backup/gengyun-20261022T063219Z.dump \
  --target-db gengyun_restore_drill --recreate
echo "exit=$?"
```

```powershell
# local：Windows 等价物，同五条判据、同退出码语义（2026-10-22 本机实跑，读数见 §9）
powershell.exe -NoProfile -ExecutionPolicy Bypass `
  -File deploy/postgres-cvm/restore-drill.ps1 `
  -PgBin 'E:\GengYunCommander\.pg17\pgsql\bin' -Database gengyun -Port 55728 `
  -WorkDir 'E:\GengYunCommander\.pg17\tmp\r31-i24-drill\work' `
  -OwnerPasswordFile 'E:\GengYunCommander\.pg17\tmp\r31-i24-drill\owner.pw'
echo "exit=$?"
```

期望输出（判据行逐条 `PASS`，末行 `PASS=24 FAIL=0`，退出码 0）：

```text
PASS 判据1/5 dump_sha256                        期望=b110f47d8a55d7de… 实际=b110f47d8a55d7de…
PASS 判据1b/5 restore_toc_entries               期望=833 实际=833
PASS 判据2/5 pg_restore --exit-on-error         期望=exit=0 且无 ERROR: 实际=exit=0；非致命 WARNING/NOTICE 0 行
PASS 判据3/5 migration_versions                 期望=0001,…,0027 实际=0001,…,0027
PASS 判据4/5 base_table_count                   期望=74 实际=74
PASS 判据4/5 view_count                         期望=8 实际=8
PASS=24 FAIL=0
exit=0
```

**失败时怎么办**：退出码 `2` 表示「缺清单、只做了结构性检查」，按**证据不完整**处理——补齐清单后重跑，不许当通过；某条判据 `FAIL` 且点名 `rows:public.某表` ⇒ 源库在备份与演练之间被写过，重做 2.1；`pg_restore` 报 `schema "…" already exists` ⇒ 目标库没清干净，加 `--recreate` 重跑（脚本只对名字含 `drill`/`restore` 的库执行 DROP）。

### 2.4 把备份搬出本机

```bash
# cvm：至少留一份在另一处（异地/对象存储由运维按额度执行）；本条只证明「搬得走且搬完还一样」
sudo cp -p /data/gengyun/backup/gengyun-20261022T063219Z.dump /data/gengyun/backup-offsite/
sudo sha256sum /data/gengyun/backup-offsite/gengyun-20261022T063219Z.dump
```

期望输出：sha256 与 §2.2 **逐位相同**。

**失败时怎么办**：哈希不同 ⇒ 拷贝不完整，重拷；目标位置不可写 ⇒ 记为「本轮无异地副本」并写进发版记录，**不要**声称已有异地备份。

## 3 迁移执行

### 3.1 先看状态，别直接 up

```bash
# cvm：up 之前先读账本，确认「已应用」与预期一致
cd /opt/gengyun
DATABASE_URL=postgres://gengyun_cvm_owner@/gengyun?host=/var/run/postgresql \
  node services/api/src/db/migrate.ts status
```

期望输出：列出 `0001..0027` 的应用状态，**未应用的恰好是本次要发的那个版本**（多一个都说明有人先跑过）。

**失败时怎么办**：连不上库 ⇒ 检查 `DATABASE_URL`（socket 路径 `/var/run/postgresql`、库名 `gengyun`）；报缺角色 ⇒ 属主角色没建，回到 §0；账本里出现预期外的版本号 ⇒ **停**，先查清是谁跑的，再决定是否继续。

### 3.2 执行迁移

```bash
# cvm
DATABASE_URL=postgres://gengyun_cvm_owner@/gengyun?host=/var/run/postgresql \
  node services/api/src/db/migrate.ts up
echo "exit=$?"
```

期望输出（本机实跑原文，27 个版本）：

```text
已应用：0001, 0002, 0003, 0004, 0005, 0006, 0007, 0008, 0009, 0010, 0011, 0012, 0013, 0014, 0015, 0016, 0017, 0018, 0019, 0020, 0021, 0022, 0023, 0024, 0025, 0026, 0027
已存在跳过：（无）
exit=0
```

**失败时怎么办**：`exit≠0` ⇒ **立刻停**，不切流量、不重启应用（旧版本还能用旧 schema 服务）。若报错发生在某个版本中途，先按 §3.3 读账本判断是「该版本未提交」还是「库里有半成品对象」；前者可直接修因重跑，后者必须先执行该版本对应的 `rollback/00NN_*.down.sql` 再重跑——`up` 不是幂等重试器，半成品状态下重跑只会二次失败。迁移失败属**阻断级**事件，按 §8 升级。

### 3.3 幂等复跑与账本核对

```bash
# cvm：第二次 up 必须什么都不做（这条是幂等性的唯一证据）
DATABASE_URL=postgres://gengyun_cvm_owner@/gengyun?host=/var/run/postgresql \
  node services/api/src/db/migrate.ts up
sudo -u postgres psql -h /var/run/postgresql -d gengyun -tAc "select count(*), min(version), max(version) from schema_migrations"
```

期望输出：

```text
已应用：（无）
27|0001|0027
```

**失败时怎么办**：第二次仍打印「已应用：…」⇒ 幂等性坏了，这本身是缺陷，停止发版并开缺陷单；账本 `count` 与迁移文件数不等 ⇒ 有人删了迁移文件或账本被手工改过，按 §8 升级，**不要**手工 `DELETE FROM schema_migrations` 去「对齐」。

## 4 服务启动与探活

### 4.1 数据库服务（迁移已成功后再确认一次）

```bash
# cvm
sudo systemctl restart gengyun-postgresql
sudo systemctl is-active gengyun-postgresql
sudo -u postgres /usr/pgsql-17/bin/pg_isready -h /var/run/postgresql
```

期望输出：

```text
active
/var/run/postgresql:5432 - accepting connections
```

**失败时怎么办**：`failed` ⇒ `sudo journalctl -u gengyun-postgresql -n 100 --no-pager` 看首条 ERROR；常见是 `pg_hba.conf` 改错、`pg_ident` 缺 map、数据目录属主错（服务以 `postgres` 用户跑）。修配置前先 `cp -p` 备份原文件——改坏 `pg_hba` 会把自己锁在门外。

### 4.2 应用侧探活

探针主机由执行者**显式提供**：本页不写死域名、也不给默认值。先在当前 shell 里 `export GY_DEPLOY_BASE_URL='https://你的生产域名'`（末尾斜杠可有可无），再执行下面的 bash 段；变量缺失或不合格时脚本**先拒绝、不发任何网络请求**，并以 `exit 2` 退出并打印原因。

```bash
# cvm / local（bash）：部署基址必须由你显式 export；缺失/不合规 ⇒ exit 2，一个请求都不发
if [ -z "${GY_DEPLOY_BASE_URL:-}" ]; then
  echo "拒绝：未设置 GY_DEPLOY_BASE_URL，请先 export 你的部署基址" >&2; exit 2
fi
case "$GY_DEPLOY_BASE_URL" in
  https://*) ;;
  *) echo "拒绝：必须以 https:// 开头，实际=[$GY_DEPLOY_BASE_URL]" >&2; exit 2 ;;
esac
host=${GY_DEPLOY_BASE_URL#https://}; host=${host%%/*}; host=${host%%:*}
case "$host" in
  ''|*.invalid|example.*|*.example.*)
    echo "拒绝：主机 [$host] 属保留域/示例域，不能当真实部署探针" >&2; exit 2 ;;
esac
PROBE_URL="${GY_DEPLOY_BASE_URL%/}/health"
# 三个字段缺一不可，200 才算活
curl -sS -o /tmp/health.json -w '%{http_code}\n' "$PROBE_URL"
cat /tmp/health.json
```

期望输出（形状与本仓库 `routes/health.ts` 一致）：

```text
200
{"status":"ok","checks":{"database":"ok"},"meta":{"execution_mode":"real"}}
```

**失败时怎么办**：`exit 2` ⇒ 前置没做对（基址没给、不是 `https://`、或主机落在保留域名上），按打印的原因改基址后重跑，**这不叫探活失败**，也**不要**为绕过校验去改这段脚本；`503` ⇒ 看 `checks.database`，为 `error` 说明应用连不上库（检查运行时角色口令与 `pg_hba` 的 `10.21.0.0/16` 行）；`200` 但 `execution_mode` 不是 `real` ⇒ 跑的是骨架/回退模式，这次发版等于没生效，按 §8 升级；连接超时 ⇒ 安全组/VPC 未放通，属「仅用户本人可做」的云侧操作。

**本节边界**：探针只回答「你显式给出的那个基址，此刻是否健康」。本页**未执行部署**、**未做云端恢复或流量切换**（见 §10），探针返回 200 不等于发版已验收。

## 5 发布后验证

四条判据全过才算「发布成功」；任一条不过就走 §7。

### 5.1 对象数量与迁移版本

```bash
# cvm
sudo -u postgres psql -h /var/run/postgresql -d gengyun -tAc "select (select count(*) from information_schema.tables where table_type='BASE TABLE' and table_schema not in ('pg_catalog','information_schema')) || ' tables, ' || (select count(*) from information_schema.tables where table_type='VIEW' and table_schema not in ('pg_catalog','information_schema')) || ' views, ' || (select count(*) from schema_migrations) || ' migrations'"
```

期望输出：

```text
74 tables, 8 views, 27 migrations
```

**失败时怎么办**：表数少于 74 ⇒ 迁移没跑全，回 §3.3；视图数不对 ⇒ 有人改了视图定义却没走迁移，**停**并查。

### 5.2 关键表行数（与备份清单逐表比对）

```bash
# cvm：清单里每一条形如 rows:public.users=2 的记录都要对上
grep '^rows:' /data/gengyun/backup/gengyun-20261022T063219Z.dump.manifest.txt | while IFS='=' read -r key want; do
  tbl=${key#rows:}
  got=$(sudo -u postgres psql -h /var/run/postgresql -d gengyun -tAc "select count(*) from $tbl")
  [ "$want" = "$got" ] && echo "OK   $tbl=$got" || echo "DIFF $tbl want=$want got=$got"
done | grep -c '^OK'
```

期望输出（18 张关键表全部一致）：

```text
18
```

**失败时怎么办**：出现 `DIFF` 且该表**本不该被本次发版写入** ⇒ 数据面异常，按 §7.4 处置；`DIFF` 出现在 `< 0` 或负数这种不可能值 ⇒ 清单格式被改坏，用 §2.2 的 `pg_restore --list` 交叉验证。

### 5.3 最小权限断言

```bash
# cvm：跑仓库自带的断言脚本，退出码 0 才算权限面没被迁移写坏
sudo -u postgres psql -h /var/run/postgresql -d gengyun -v ON_ERROR_STOP=1 \
  -f /opt/gengyun/deploy/postgres-cvm/sql/90-assert-least-privilege.sql
echo "exit=$?"
```

期望输出（脚本内会**故意**探测越权路径，出现 `permission denied for table …` 的 ERROR 行是预期，退出码仍为 0）：

```text
ok
exit=0
```

**失败时怎么办**：退出码非 0 ⇒ 某条断言真的不成立（不是预期的 denied 探测），`ON_ERROR_STOP` 会停在第一条；按报错表名反查本次迁移有没有误 `GRANT ALL`。这类问题只允许「改迁移脚本的下一个版本修」，**不许**手工 `REVOKE` 掩盖——手工改的权限不在账本里，下次发版会再丢。

### 5.4 回归读数

```bash
# local：与 §1.3 同一条命令、同一个端点，比 p95
for i in $(seq 1 200); do curl -s -o /dev/null -w '%{time_total}\n' "http://127.0.0.1:3310/api/v1/knowledge?limit=20"; done | sort -n | awk '{a[NR]=$1} END {printf "p95=%.3f ms n=%d\n", a[int(NR*0.95)]*1000, NR}'
```

期望输出：p95 不超过 §1.3 基线的 **2 倍**（本机基线 12.6 ms ⇒ 25 ms）。

**失败时怎么办**：超阈值但错误率为 0 ⇒ 先排除测量噪声（同一分钟再取一次），仍超则按 §7 判据 R2 处理；错误率也起来了 ⇒ 直接按 R1 回滚，不做二次测量。

## 6 灰度与放量判据

放量按 10% → 50% → 100% 三档，每档**观察满 30 分钟**且下面四条全绿才进下一档。判据与 §7 的回滚触发条件同源，只是「放量档位」不同。

| 档位 | 进入条件 | 观察窗口 | 全部满足才继续 |
| --- | --- | --- | --- |
| 10% | §5 四条判据全过 | 30 min | 5xx ≤ 0.2%；核心读接口 p95 ≤ 基线 1.3 倍；`/health` 0 次失败；无 P0 告警 |
| 50% | 10% 档观察期全绿 | 30 min | 5xx ≤ 0.5%；p95 ≤ 基线 1.6 倍；`/health` 0 次失败；连接池等待 ≤ 0 |
| 100% | 50% 档观察期全绿 | 60 min | 5xx ≤ 1.0%；p95 ≤ 基线 2.0 倍；`/health` 0 次失败；错误预算未被打穿 |

**判据读数怎么取**（每档开档前取一次、观察期结束时取一次）：

```bash
# cvm：从数据库侧看连接池是否被打满（最容易被忽略的一条）
sudo -u postgres psql -h /var/run/postgresql -d gengyun -tAc "select state, count(*) from pg_stat_activity where datname='gengyun' group by state order by 2 desc"
```

期望输出（`idle` 占多数、无长期 `active` 堆积）：

```text
idle|6
active|1
```

**失败时怎么办**：`active` 持续大于连接池上限的一半且 60 秒不降 ⇒ 按判据 R6 处理；某一档判据红 ⇒ **回到上一档**（不是回到 0），上一档也红才整体回滚；观察窗口没满就想放量 ⇒ 不许，窗口本身就是判据的一部分。

## 7 回滚

### 7.1 回滚触发条件（可量化，命中任一即回滚）

| # | 判据 | 阈值 | 观察窗口 | 读数来源 |
| --- | --- | --- | --- | --- |
| R1 | HTTP 5xx 占比 | 大于 **1.0%** | 连续 **5 分钟** | 网关/访问日志聚合 |
| R2 | 核心读接口 p95 | 大于发版前基线 **2 倍**（本机基线 12.6 ms ⇒ 25 ms） | 连续 **10 分钟** | §1.3 / §5.4 同口径取样 |
| R3 | `/health` 连续失败 | **3 次**（探针每 10 s 一次，30 s 内连失 3 次） | 30 秒 | 探针历史 |
| R4 | 迁移执行失败 | `migrate up` 退出码非 0，或 `schema_migrations` 行数不等于 **27** | 一次即触发 | §3.2 / §3.3 |
| R5 | 关键表行数与备份清单不符 | 任一表不一致（§5.2 出现 `DIFF`） | 一次即触发 | §5.2 |
| R6 | 连接池耗尽 | 等待连接的请求大于 0 且持续 **60 秒** | 60 秒 | §6 的 `pg_stat_activity` |
| R7 | 错误预算 | R1 与 R2 在 **15 分钟**内同时命中 | — | — |

**R1 与 R2 同时命中 ⇒ 立即回滚，不再观察**：两条独立指标同时劣化，通常意味着不是噪声而是真故障。

### 7.2 应用侧回滚（先做这一步，最快）

```bash
# cvm / 云托管控制台：把流量切回上一个可用 revision，不要重建、不要改配置
# 命令行不可用时的等价判据：切回后 /health 必须 200 且 execution_mode=real
# 基址同 §4.2，由你显式 export（本页不写死域名；校验缺失时先跑 §4.2 的拒绝段）
curl -sS -o /tmp/health.json -w '%{http_code}\n' "${GY_DEPLOY_BASE_URL%/}/health"
```

期望输出：

```text
200
```

**失败时怎么办**：切回后仍 `503` ⇒ 问题不在应用版本而在库（迁移已改变 schema），继续 §7.4；切不回去（旧 revision 已被删）⇒ 这是发布流程缺陷，按 §8 升级并记录：**旧 revision 的保留期必须长于一个观察周期**。

### 7.3 回滚判据复测

```bash
# local：回滚后 5 分钟内用与 §5.4 完全相同的口径复测，确认读数回到基线
for i in $(seq 1 200); do curl -s -o /dev/null -w '%{time_total}\n' "http://127.0.0.1:3310/api/v1/knowledge?limit=20"; done | sort -n | awk '{a[NR]=$1} END {printf "p95=%.3f ms n=%d\n", a[int(NR*0.95)]*1000, NR}'
```

期望输出：p95 回到基线的 1.3 倍以内。

**失败时怎么办**：回滚后读数不降 ⇒ 说明劣化与本次版本无关（外部依赖、数据量、机器负载），此时**不要**反复回滚，转 §8 按「非版本原因」分诊。

### 7.4 数据库回滚（只在 R4/R5 命中时做）

**这条最容易出事，先说清楚边界**：`migrate.ts` **没有 down 命令**，`migrations/rollback/` 下的 26 个 down 脚本只能手工执行；它们能撤销 schema 变更，**不能**撤销被新代码写进去的数据。

```bash
# cvm：① 先确认要撤到哪个版本（当前账本与目标版本）
sudo -u postgres psql -h /var/run/postgresql -d gengyun -tAc "select version from schema_migrations order by version desc limit 3"
# ② 逐个执行 down 脚本（从高到低，一次一个，每步都看一眼）
sudo -u postgres psql -h /var/run/postgresql -d gengyun -v ON_ERROR_STOP=1 \
  -f /opt/gengyun/services/api/db/migrations/rollback/0027_*.down.sql
echo "exit=$?"
```

期望输出（撤到目标版本前，账本最大值每步减一）：

```text
0027
0026
0025
exit=0
```

**失败时怎么办**：`ON_ERROR_STOP` 停在某条 ⇒ **不要**手工删对象强行继续，先确认该 down 脚本是否依赖数据（有 `DROP COLUMN` 的脚本在列被写过之后可能失败）；撤不动就停在这里，用 §2.3 演练过的备份做**整库恢复**（这条路径 2026-10-22 已实跑，读数见 §9）。**⛔ 绝不允许**在没做 §2.3 的库上执行整库恢复。

### 7.5 回滚后必须补的动作

```bash
# cvm：留一条可追溯的记录，写清回滚到哪个版本、原因命中哪条判据
sudo -u postgres psql -h /var/run/postgresql -d gengyun -tAc "select count(*), max(version) from schema_migrations"
```

期望输出：与回滚目标一致（例如撤到 0026 则为 `26|0026`）。

**失败时怎么办**：读数与预期不符 ⇒ 回滚没完成，**不要**宣布已回滚；按 §8 升级，并保持流量停在旧版本。

### 9.3 「删库 → 恢复」全链路（本次新增的真删库取证）

前一次演练（`docs/verification/gy-i24-restore-drill-local-20261018.md`）只恢复到**另一个库**，源库始终在，因此没证明「库没了也能回来」。本次补上这一段：

| 阶段 | 命令 | 读数 |
| --- | --- | --- |
| ① 删库前快照 | `psql -tAc "select count(*) …"` | `users=2 media=1 jobs=1 tables=74 views=8 ledger=27` |
| ② 真删库 | `dropdb -h 127.0.0.1 -p 55728 -U gengyun_cvm_owner gengyun` | `DROP_EXIT=0`；`pg_database` 中 `gengyun` 计数 **0**；再连报 `FATAL:  database "gengyun" does not exist`（exit 2） |
| ③ 重建空库 | `createdb -O gengyun_cvm_owner -T template0 -E UTF8 gengyun` | `CREATEDB_EXIT=0` |
| ④ 从 dump 恢复 | `pg_restore --exit-on-error --no-password` | `RESTORE_EXIT=0`；恢复日志 **0 字节**；致命行 **0** |
| ⑤ 恢复后快照 | 同 ① 的 SQL | `users=2 media=1 jobs=1 tables=74 views=8 ledger=27` |
| ⑥ 逐表比对 | 清单 18 条 `rows:` 逐条 `count(*)` | `KEY_TABLES=18 MISMATCH=0` |
| ⑦ 内容抽查 | `select sha256 from media` | `a1a1…a1a1`（32 字节，与种子一致）；`schema_migrations` = 27 个版本 |

①⑤ **完全一致**，⑥ 逐表零差异 ⇒ 「删库后能从备份回到原状」这一条成立。

**负控制（证明②不是多余的一步）**：在**已灌满数据**的库上直接重放恢复（不删库）：

```bash
# 期望失败：目标库有残留对象
pg_restore -h 127.0.0.1 -p 55728 -U gengyun_cvm_owner -d gengyun --exit-on-error --no-password gengyun-gengyun-20261022T063219Z.dump
echo "exit=$?"
```

实测输出：

```text
pg_restore: error: could not execute query: ERROR:  schema "catalog_ops" already exists
exit=1
```

⇒ 恢复前必须先 `dropdb`/`createdb`（或对隔离库 `--recreate`），否则得到的是「一半旧一半新」的库。这条负控制同时也证明 `--exit-on-error` 真的会在第一个结构性冲突处停下，而不是「跑完再说」。
