## 0 门禁边界与证据字段口径（人工补记，生成区之外）

`node tools/verify-contract-status.mjs` 的证据校验是**存在性**判定，不判定证据与操作的语义对应：`tools/verify-contract-status.mjs:89` 用 `text.includes(item.name)` 判断给定片段是否出现在被引用文件里，`tools/verify-contract-status.mjs:91-94` 只校验 `lines` 的格式与是否落在文件行数内。两者与 owner、路由处理器、操作语义**零绑定**，所以语义上指错地方、指错操作的引用同样能过门禁；工具首行与末行也自述「不证明语义正确、真实能力或整项验收」。下列边界与口径由证据校正片补记，供后续核对者沿用同一口径。

- 实测（仓外 detached 副本，工具判定逻辑未改，plain 与 `--write-doc` 两臂各跑一次）：把 `verifyOCR` 的证据区间改指 `createOCR` 处理器 `224-257`、把 `getOCR` 与 `deleteOCR` 的证据区间互换、把 `verifyOCR` 的区间放宽到整个文件、把 `verifyOCR` 的证据片段改成同文件里 `deleteOCR` 的断言原文，这四个语义变异在 `--write-doc` 臂**全部被接受**（exit 0）。plain 臂对这四个变异确实报 FAIL，但报的是「中文对照表与 JSON 不一致；核对状态后使用 --write-doc 同步表格」——那是表格未同步的**假红**，不是语义发现；按提示同步后，错误区间会被写进本文件的对照表，从此完全不可见。
- 门禁仍然拦得住的是形状类错误：`lines` 越界、`path` 不存在或指向目录、`lines` 缺 `-`、同一项同时给 `path` 与 `test`、片段在被引用文件里找不到。
- 证据项的 `name` 字段口径是**可定位文本片段**（定位操作行为用的稳定子串），不要求等于某个用例名；`name` 只在给出 `test` 时出现。全表 141 条带 `name` 的证据中，等于注册标题原文的 32 条、标题真前缀 70 条、标题中段子串 39 条，子串判定是工具的既有设计。工具报错文案仍写「找不到用例名」，该文案由 `tests/unit/contract-status-tool.test.mjs:120` 的断言冻结（`tests/**` 不在本片改动范围），仅文案与字段口径不一致，不影响判定。

## 6 可回归校验

在仓库根目录运行：

```powershell
node tools/verify-contract-status.mjs
node tools/verify-contract-status.mjs --runtime
node --test tests/unit/contract-status-tool.test.mjs
```

默认校验无需安装依赖，检查 112 条操作及 8 个维度覆盖、证据路径/行号/可定位文本片段、路由注册和中文表格一致性。静态扫描跟随 app.ts 实际导入并调用的 register*，支持 routes 目录之外的注册模块；仅存在文件或注释中的调用不计装配。

`--runtime` 需要项目锁定依赖和 Node 24，在清除业务配置、凭据与 NODE_OPTIONS 的子进程中调用实际 buildApp、ready 和 Fastify.hasRoute。使用 stub，不监听端口、不发 HTTP/供应商请求、不连接数据库。它证明当前注册清单，不能证明响应、鉴权、状态语义或真实能力。

先人工核对 JSON 的状态/证据，再运行 `node tools/verify-contract-status.mjs --write-doc` 同步标记区域中的表格。覆盖、装配或证据失败时不写文档；普通校验只读，检测陈旧表格后失败退出。脚本是独立命令，未追加 CI 工作流或修改 package.json；其回归测试由现有 unit 通配命令发现。

静态扫描使用正则，不是 TypeScript AST，只支持当前具名相对导入、直接 register*(app, ...) 与 app.get/post/put/patch/delete 写法，显式展开 API_PREFIX 和 crops/regions。模块内多注册函数、动态导入/条件注册、更多模板或插件 prefix 需要扩展扫描并用 runtime 模式核对，不据扫描成功推断任意装配写法正确。
