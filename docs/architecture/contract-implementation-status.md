## 0 门禁边界与证据字段口径（人工补记，生成区之外）

`node tools/verify-contract-status.mjs` 的证据校验分三层：**形状**（`checkEntry`：`path`/`test` 二选一、仓库内存在、`lines` 格式与文件行数内、`name` 与锚点文本在被引用文件里找得到）、**锚点**（`checkAnchors`：引用自带 `symbol` 或 `anchor` 时，锚点文本必须出现在引用行范围内，容差 ±2 行，覆盖 operations 与 dimensions；无锚点只计「不可核」并列可疑，不判红；所有带行号引用另量区间内容，整段仅空白/收尾行或首行为空行只计可疑不判红）与**语义**（`checkSemantics`：路由注册块与断言区间）。三层都只判「引用位置与操作身份可证伪地冲突」，不判定证据与操作的语义对应，也不与 owner、路由处理器、操作语义绑定；基线 `56042f7` 实测 409 条证据中 `symbol`/`anchor` 命中 0 条（141 条 `name` 只能证「文件里出现过」，268 条无锚点只计不可核、「区间内」档恒 0）——这是**历史读数，不是现状**。R28-S50／[#362](https://github.com/GengYunChuChao/GengYun/pull/362)（squash `9cfd3e4`，合入 main 的 `b42d921`）已给 229 条纯行号引用逐条写入真实 `symbol`，锚点层「区间内」档由恒 0 变为 229 条真在跑；基线 `76b0e86` 实测（`node tools/verify-contract-status.mjs`，exit 0）为：证据锚点 370 条引用自带锚点（区间内 229 条 + 仅整文件 141 条），无锚点不可核 39 条（纯行号 0 + 无行号源文件 9 + 无用例名 30），合计仍是 409 条、未增删任何引用；余下 141 条只有 `name` 且无 `lines`，只能证明「该串在该文件里出现过」，进不了「区间内」档；工具口径的「纯行号区间」仍是 229 条（有实质内容 229 条；整段仅空白/收尾行 0 条、区间首行为空行 2 条，只计可疑不判红），该档量的是区间内容、与是否带锚点无关。**锚点边界不因这 229 条而放宽**：锚点只证明「该符号出现在该引用行区间内（容差 ±2 行）」，不证明证据与操作的语义对应，符号恰落在区间内而语义指错地方、指错操作的引用仍可能过门禁；本段在生成区（`contract-status-tables` 标记区）之外，`--write-doc` 只重生成表格、不重写本段，故只能人工维护；工具首行与末行也自述「不证明语义正确、真实能力或整项验收」。下列边界与口径由证据校正片补记，供后续核对者沿用同一口径。

- 实测（仓外 detached 副本，工具判定逻辑未改，plain 与 `--write-doc` 两臂各跑一次）：把 `verifyOCR` 的证据区间改指 `createOCR` 处理器 `224-257`、把 `getOCR` 与 `deleteOCR` 的证据区间互换、把 `verifyOCR` 的区间放宽到整个文件、把 `verifyOCR` 的证据片段改成同文件里 `deleteOCR` 的断言原文，这四个语义变异在 `--write-doc` 臂**全部被接受**（exit 0）。plain 臂对这四个变异确实报 FAIL，但报的是「中文对照表与 JSON 不一致；核对状态后使用 --write-doc 同步表格」——那是表格未同步的**假红**，不是语义发现；按提示同步后，错误区间会被写进本文件的对照表，从此完全不可见。
- 门禁仍然拦得住的是形式类错误：`lines` 越界、`path` 不存在或指向目录、`lines` 缺 `-`、同一项同时给 `path` 与 `test`、片段在被引用文件里找不到；自锚点校验片起还拦「`symbol`/`anchor` 在文件里根本不存在」「锚点存在但落在引用行范围外（±2 行，计语义错误）」与「`symbol` 与 `anchor` 同给且取值不同」。
- 证据项的 `name` 字段口径是**可定位文本片段**（定位操作行为用的稳定子串），不要求等于某个用例名；`name` 只在给出 `test` 时出现。全表 141 条带 `name` 的证据中，等于注册标题原文的 32 条、标题真前缀 70 条、标题中段子串 39 条，子串判定是工具的既有设计。工具报错文案仍写「找不到用例名」，该文案由 `tests/unit/contract-status-tool.test.mjs:120` 的断言冻结（`tests/**` 不在本片改动范围），仅文案与字段口径不一致，不影响判定。

**锚点两种形态（R31 起）**：行号形态 `lines: "起-止"` 与符号形态 `locator: {symbol, file?}` 二选一，同给即形状错误。符号形态在运行时用 `tools/lib/anchor-resolve.mjs` 的同一套归属块口径（与 `--reanchor` 落盘同源）解析成当前行范围：解析失败（MISSING 0 候选／NO_BLOCK 声明无块体／AMBIGUOUS 多候选）一律**形状错误 ⇒ exit 1 并列出候选**，不许降级成「不可核」。台账里不存数字，`--write-doc` 把这类证据渲染成 `path#符号`（不写解析出的行号：那张表是逐字比对的，写数字等于把漂移搬进文档）；当前解析值在每次运行的 `PASS: 符号形态锚点 …` 行里给出。样板：`requestAccountDeletion` 引用 `services/api/src/app.ts` 的那一条已改为 `locator: {symbol: "registerAccountDeletionRoutes"}`（基线 `489804e4` 解析为 1826-1833）。读数、负控制与取舍见 [gy-r31-anchor-symbol-20261022.md](../verification/gy-r31-anchor-symbol-20261022.md)。一条容易被误读的边界（实测）：**往 app.ts 头部插 10 行时行号形态并不会变红**——首命中从 1825 漂到 1835，而容差上界是区间终点 1833 + 2 = 1835，恰好压线；插 11 行（首命中 1836）才是 exit 1、语义错误 1 条。所以旧形态的「漂移 10 行」不是「能被发现」，而是「错得刚好没被发现」，这正是本片要治的病。

## 6 可回归校验

在仓库根目录运行：

```powershell
node tools/verify-contract-status.mjs
node tools/verify-contract-status.mjs --runtime
node --test tests/unit/contract-status-tool.test.mjs
```

默认校验无需安装依赖，检查 112 条操作及 8 个维度覆盖、证据路径/行号/可定位文本片段、路由注册和中文表格一致性。静态扫描跟随 app.ts 实际导入并调用的 register*，支持 routes 目录之外的注册模块；仅存在文件或注释中的调用不计装配。

`--runtime` 需要项目锁定依赖和 Node 24，在清除业务配置、凭据与 NODE_OPTIONS 的子进程中调用实际 buildApp、ready 和 Fastify.hasRoute。使用 stub，不监听端口、不发 HTTP/供应商请求、不连接数据库。它证明当前注册清单，不能证明响应、鉴权、状态语义或真实能力。

先人工核对 JSON 的状态/证据，再运行 `node tools/verify-contract-status.mjs --write-doc` 同步标记区域中的表格。覆盖、装配或证据失败时不写文档；普通校验只读，检测陈旧表格后失败退出。脚本是独立命令，未追加 CI 工作流或修改 package.json；其回归测试由现有 unit 通配命令发现。

静态扫描使用正则，不是 TypeScript AST，只支持当前具名相对导入、直接 register*(app, ...) 与 app.get/post/put/patch/delete 写法，显式展开 API_PREFIX 和 crops/regions。模块内多注册函数、动态导入/条件注册、更多模板或插件 prefix 需要扩展扫描并用 runtime 模式核对，不据扫描成功推断任意装配写法正确。
