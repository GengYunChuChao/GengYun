# ADR-002 识别供应商接入路线

日期：2026-11-06；关联：`#1003`（识别协议接收面）、`#1004`/`#1006`（授权面必须显式选接收方）。状态：**待产品裁定，未冻结**。本页只做路线判定，不含任何准确率或能力主张。

## 背景与事实

- 仓库内已有**出站**真实识别适配器 `services/api/src/recognitions/live-adapter.ts`，它按冻结剖面 `LIVE_RECOGNITION_FROZEN_PROFILE`（协议 `gy-recognition-live-v1`、单图上限 2 MiB、`inlineBase64` 传输、超时 1–20 s、零重试、候选上限 3）调用运维给定的 `https` 端点。它只产出候选与原因，**不决定任务状态**。
- 仓库内**没有**对端：`gy-recognition-live-v1` 只是我们自己的形状，任何厂商都不原生说这个协议。
- 2026-11-06 的真机走查里，这一层由**仓库外**的本地适配器承担：它把 `gy-recognition-live-v1` 翻成某供应商的 OpenAI 兼容 `chat/completions` 视觉调用。链路通了，但**这一段不在仓库里**，生产环境无法据此上线。
- 口径边界：基线仍「没有已审识别供应商、零真实调用、零准确率证据」（`docs/architecture/ai-ops-spec-status.md`）。演示环境的真实调用不改变这条基线。
- 2026-11-08 按实现复核（`#1003` 的「怎么切供应商」照这两条配）：仓内是**两个并列剖面**——`gy-recognition-live-v1`（`services/api/src/recognitions/live-adapter.ts`）与 `openai-vision-v1`（`services/api/src/recognitions/openai-vision-adapter.ts`，选项 A 的骨架：零真实供应商、零真实调用、零准确率证据），互不替换；由 `RECOGNITION_PROVIDER_PROFILE` 选路（`services/api/src/recognitions/provider.ts:230-231`），只有显式写 `openai-vision-v1` 才切到新剖面，缺省／留空／写错值（不报错）**仍走 live 剖面，live 仍是默认**（`services/api/src/recognitions/provider.ts:248`）。
- `RECOGNITION_PROVIDER_MODEL` 只在新剖面下必填且**无默认模型名**：缺它 ⇒ 新剖面装配失败、受理前 503 `PROVIDER_UNAVAILABLE`，不回落 live（`services/api/src/recognitions/openai-vision-adapter.ts:203-204`）。注：下方「选项 A」第三条的「未配置即 fail-closed」是选项描述里的期望形态，与今天的实现不同（未配置走的是既有剖面，不是 fail-closed）；本页不改该条措辞，只在此记实。

## 选项

### A 新增「供应商剖面 + 适配器」（推荐）

在 `services/api/src/recognitions/` 下再实现**一个** `RecognitionProvider`：

- 新冻结剖面（例如 `openai-vision-v1`）：端点、模型名、图像编码方式、超时区间、候选上限独立冻结，与 `gy-recognition-live-v1` 并列而非替换。
- 复用既有闸门骨架：`build(本地) → reserve(闸门) → send(恰好一次) → settle(无论成败)`；`redirect:'manual'`、`AbortSignal.timeout`、零重试、错误码只取 `PROVIDER_FAILURE_CODES` 的四个成员。
- 由环境变量选择剖面，两个剖面互斥；未配置即 fail-closed，不回落替身。

代价：多一套剖面常量、映射表与负控制测试；供应商形状（提示词、JSON 解析）进入仓库。

收益：不新增部署单元、不改冻结契约、照片出网路径最短且可审计；供应商错误可映射到既有四个错误码；演示用的仓外适配器可以退役。

### B 契约换代

把 `gy-recognition-live-v1` 扩成能直接承载厂商字段（提示词、模型参数、返回结构）。

代价：冻结契约要随每个供应商的形状变化，客户端与评测都被牵动；历史上 `gy-*-live-v1` 的价值正是「对外形状稳定、对内可换供应商」。

收益：不需要第二个剖面。

判定：**不推荐**。用契约吸收供应商差异，等于把可替换性换成一次性便利。

### C 仓库内新增独立 bridge 服务

把演示用的适配器整体搬进仓库，作为独立进程/部署单元。

代价：多一个进程、多一份部署与运维面、多一条内部网络跳；还要在仓库内定义它与 API 之间的协议（否则就是把同一份翻译搬个位置）。

收益：API 完全不感知供应商。

判定：**只在前置条件成立时采用**——即确实需要「一个 bridge 对接多家供应商」或「供应商只能在另一网络域访问」。当前两者都不成立。

## 决策

**推荐 A**，理由按优先级：

1. **不动物理边界**：照片仍由 API 直接出网到已授权接收方，外发账本、用途校验、接收方核验都在同一条路径上；bridge 会在中间多一跳，账本与真实出网之间出现空隙。
2. **不动冻结契约**：`gy-recognition-live-v1` 保持不变，已有适配器、测试与文档全部继续有效。
3. **成本最低**：不需要新部署单元，不需要新的内部协议。

## A 的前置（未完成前不得上线）

1. **供应商评审**：留存期、是否用于训练、删除证据三项要落到 `recipients` 的核验字段上；未核验的接收方不得出现在授权面。当前没有任何供应商通过这项评审。
2. **权限与隐私**：`external_inference` 用途的授权必须显式选定该接收方（客户端已改、服务端已有条件强制）；不得用运营方预置绑定代替用户选择。
3. **凭据边界**：密钥只在进程内使用，不落盘、不入仓库、不进日志；错误信息不回显请求体。
4. **可观测性**：每次调用只记供应商名、模型名、耗时、token 计数与错误码，不记录图像内容或可还原摘要。
5. **证据口径**：上线前必须有真实调用记录与失败态记录；在那之前，文档继续写「未接入已审供应商」。

## 影响面（若采纳 A）

- 新增：一个剖面常量文件、一个适配器实现、一组单测（含每个错误码的负控制）、一组集成测试（用本地假供应商，不联网）。
- 修改：装配处按环境变量选择剖面；`AI_ENDPOINTS` 增加一条识别端点条目；运营文档补「如何配置剖面与端点」。
- 不动：契约、迁移、`gy-recognition-live-v1` 剖面、既有错误码集合。

## 非目标

- 不做准确率评测、不做供应商横向对比、不引入模型微调。
- 不因本 ADR 修改任何既有验收口径，也不关闭任何 issue。

## 待裁定问题

1. 是否采纳 A？若采纳，先做剖面常量与适配器骨架（不含真实密钥），还是先补供应商评审材料？
2. 若产品倾向「暂不接任何外部供应商」，则 `#1003` 应改为「仅保留仓外演示适配器」并明确不进入生产，是否接受？
