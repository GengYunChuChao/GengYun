## 2. 语义判定：#1030 的「上限」到底是谁的上限

派单里给了两个候选（「每帖 ≤3」⇒ 第 4 张上传应 201；「每用户待用池 ≤3」⇒ 第 4 张上传就该被拒）。读代码后判定：**两个候选各对一半，落在两个不同的裁决点上**；上传侧走的是「待用池」，挂载侧走的是「每帖」。

### 2.1 上传侧 = 每用户「待用池」≤3

- `services/api/src/media/service.ts:968-969`：`const mediaCountForPost = await attachmentLimitFor(actor, purpose);` 之后把读数交给 `validateUploadInput(input, { mediaCountForPost })`。
- `services/api/src/media/service.ts:840-856` `async function attachmentLimitFor(actor, purpose)`：非 `community_image` 直接返回 0；`community_image` 读计数端口；端口返回 `null` ⇒ 抛 `PROVIDER_UNAVAILABLE` + `retryable: false` + `details: [{ field: '/purpose', code: 'post_image_limit_unwired' }]`（文案常量在 `services/api/src/media/service.ts:358`，`createUnwiredAttachmentCounter()` 在 `services/api/src/media/service.ts:327`）。
- `packages/media/validate.mjs:84-91`：`mediaCountForPost >= COMMUNITY_MAX_IMAGES_PER_POST`（= 3，`packages/media/constants.mjs:75`）⇒ 抛 `invalidRequest('每个帖子最多 3 张图片', [{ field: '/purpose', code: 'post_image_limit' }])`。
- 计数端口的真实现是 `services/api/src/media/store-pg.ts:365-385` 的 `countPendingCommunityImages(ownerId)`：

  ```sql
  SELECT count(*) AS count FROM public.media m
   WHERE m.owner_id = $1::uuid
     AND m.purpose = 'community_image'
     AND m.state IN ('initiated','uploaded','processing','ready')
     AND m.created_at > now() - interval '24 hours'
     AND NOT EXISTS (SELECT 1 FROM public.post_media_attachments a
                       JOIN public.community_posts p ON p.id = a.post_id
                      WHERE a.media_id = m.id AND p.visibility <> 'deleted')
  ```

  ⇒ 它数的是**在途、还没挂到「未删除的帖子」上的图**。**挂载即释放**、**删帖即释放**、**24h 自衰减**。
- 反证口径：同一文件 `services/api/src/media/store-pg.ts:342` 的 `liveCommunityImageCount(ownerId)` 是「owner 生命周期累计」，`services/api/src/media/service.ts:826-838` 明令禁止拿它顶替待用池——本次 PASS 7 用「A 名下累计 7 行 media 仍可继续挂载」把这条反证钉住。
- 装配判定：`services/api/src/media/service.ts:1693-1701` `defaultAttachmentCounter(executionMode, persistence)`——real 且 persistence 带 `countPendingCommunityImages` ⇒ `createPostgresAttachmentCounter`；缺 ⇒ `createUnwiredAttachmentCounter()`（恒 `null` ⇒ 上传面 503）。real + `pool` 时 `services/api/src/app.ts:1299-1306` 默认就接 `createPostgresMediaStore`，所以计数口默认是接线的——这也解释了为什么 fail-closed 用例必须**显式注入一个摘掉该方法的媒体库**才复现。

### 2.2 挂载侧 = 每帖 ≤3；`#1057` 之后 HTTP 首拒变成路由层的 `post_image_limit`

- 路由 schema：`services/api/src/routes/community.ts:75` `required: ['title','body','media_ids']`、`services/api/src/routes/community.ts:81-86` `media_ids: { type: 'array', maxItems: 3, uniqueItems: true, items: { type: 'string', format: 'uuid' } }`。
- **`#1057` 之前**：第 4 个 id 在 schema 校验这一步就失败，`services/api/src/app.ts:2732` 把它映射成 `400 INVALID_REQUEST`「请求校验失败」，`details: [{ field: item.instancePath || '/', code: item.message }]` ⇒ `code` 是 ajv 的 `must NOT have more than 3 items`。
- **`#1057`（`da96c9b6`）之后**：`services/api/src/routes/community.ts:214`（`POST /posts`）与 `services/api/src/routes/community.ts:235`（`PATCH /posts/:id`）都挂了 `preValidation: rejectMediaIdsOverflow`（函数体 `services/api/src/routes/community.ts:479`；判据在 `:482`「数组长度 > `MAX_MEDIA_IDS_PER_POST`（= `postBody.properties.media_ids.maxItems`，`:426`）」，抛在 `:483-485`）。Fastify 的 `preValidation` **先于** schema 校验跑 ⇒ 首拒变成 `400 INVALID_REQUEST` + `details[0] = { field: '/media_ids', code: 'post_image_limit' }` + `message = 每个帖子最多 3 张图片`；ajv 那句英文文案在 main 上**已经拿不到**。
- 再往下才是结构约束：0022 的数组 CHECK 与 0056 的 `UNIQUE(post_id, ordinal)` / `CHECK (ordinal BETWEEN 1 AND 3)`；`services/api/src/community/store-pg.ts:397-454` `claimPostMedia()` 落库，`services/api/src/community/store-pg.ts:457` `postImageLimitError()`（`details: [{ field: '/media_ids', code: 'post_image_limit' }]`，`services/api/src/community/store-pg.ts:477-478` 由 23514/23505 触发、`services/api/src/community/store-pg.ts:493` 由数组溢出预检触发）。
- ⇒ **HTTP 面上可达的 `/media_ids` + `post_image_limit` 来自路由层 `preValidation`，不是 store**：store 那条 `postImageLimitError()` 经 HTTP **仍不可达**——`preValidation` 在进服务层之前就抢先拒了，`maxItems:3` 也保证结构约束不会被 HTTP 走到（store 侧那条仍只在直调 store 的集成面里可达，见既有 `tests/integration/post-media-attachments-pg.mjs`）。PASS 5 因此写成**正控制**：断言 `details[0]` 逐字等于 `{ field: '/media_ids', code: 'post_image_limit' }`、`message` 逐字等于「每个帖子最多 3 张图片」；再把同一个 4 元数组打到**不存在的 post id** —— 拿到的仍是同一个 `field`+`code` 指纹 ⇒ 钉住「**该指纹不需要帖子行**」（store 的 `postImageLimitError()` 要先查到真行才判上限，故可排除 store 裁决）。⚠ 这个探针的证明力只到指纹这一级：单看「400」区分不了 ajv／preValidation／服务层（实测把 `preValidation` 摘掉后，未知 post id 仍以 ajv 信封返回 400），与 ajv 的区分只靠上面那两处逐字断言。

### 2.3 判定表

| 候选语义 | 实现位置 | 谁最先裁决 | real 模式 HTTP 首拒信封 | 本次断言 |
| --- | --- | --- | --- | --- |
| 每用户待用池 ≤3 | `services/api/src/media/store-pg.ts:365-385` + `services/api/src/media/service.ts:840-856` | 媒体上传服务 | `400 INVALID_REQUEST` + `details[0]={"field":"/purpose","code":"post_image_limit"}` + `retryable:false` | PASS 2 / 4 / 6 |
| 每帖 ≤3 | `services/api/src/routes/community.ts:81-86` schema → `services/api/src/routes/community.ts:479` 的 `preValidation` → 0022 CHECK / 0056 约束 | 路由层 `preValidation`（`#1057` 之后；之前是路由 schema） | `400 INVALID_REQUEST` + `details[0]={"field":"/media_ids","code":"post_image_limit"}` + `message="每个帖子最多 3 张图片"` | PASS 5（正控制 + 「不存在的 post id 也拿到同一指纹」的指纹探针） |
| owner 生命周期累计 | `services/api/src/media/store-pg.ts:342` | **不参与上限** | — | PASS 7 反证 |

⇒ 由此定断言：**「3 张挂到帖 A ⇒ 第 4 张上传 201」在真实实现下不成立**，必须先挂载（腾空待用池）再上传；用例因此把这两件事拆成 PASS 2（未腾空 ⇒ 400）与 PASS 4（腾空后 ⇒ 201），两个读数都在同一进程里取得。

## 7. 边界：这份证据不证明什么

- **合成声明**：对象存储是合成 S3 兼容端点（零外呼、零 PUT），审核域是合成端口（`provider.synthetic === true`），PG 是本次临时簇（跑完即删）。这些都不代表真实对象存储、真实审核供应商、生产库的能力。
- **不走 `/complete`**：全程停在 `initiated`，因此不覆盖「上传完成 ⇒ ready ⇒ 再挂载」这条状态迁移；待用池把 `initiated/uploaded/processing/ready` 都算在途，语义上不受影响，但没有逐个状态实测。

- **24h 自衰减未测**：需要时间穿越（改 `created_at` 或冻结时钟），本次未覆盖。
- **`/media_ids` 的 `post_image_limit` 只证到路由层**：main 上它是 `#1057` 的 `preValidation` 抢先抛的（PASS 5 正控制 + 「不存在的 post id 也同信封」）。store 侧那条 `postImageLimitError()`（同一 `field`/`code`）**仍没有** HTTP 证据——`preValidation` 让它经 HTTP 不可达，本页不为它背书（覆盖仍在既有直调 store 的 `tests/integration/post-media-attachments-pg.mjs`）。
