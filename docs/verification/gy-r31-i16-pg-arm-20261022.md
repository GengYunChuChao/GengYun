## 4. 非空证明（原文）

**做法（为什么不是「改夹具」）**：本臂的「真库」证据依赖 `app.ts` 的装配分支。把装配换成内存实现有两条路：

1. 让 `config.executionMode !== 'real'` ⇒ 但那样 `favoritesService` 会变成 `null`，路由直接 503，红的会是**HTTP 状态码**（夹具失败），不是「库里没有那行」——**这是假红**，证明不了读数。
2. 只把 store 换成内存实现、且**让它自称 `persistent: true`** ⇒ 服务层门禁（`services/api/src/app.ts:1431-1448` 判定 `!store.persistent`）放行，HTTP 面照常 `201`，于是红的只可能是「SQL 里查不到那行」——**这才是对读数的直接否定**。

本次用的是第 2 条：`GY_I16_FORCE_MEMORY=1` 时 `tests/integration/favorites-history-pg.mjs:346` 注入

```js
favoritesInjection.store = Object.assign(createMemoryFavoritesStore({ now }), { persistent: true })
```

（`persistent` 在 `services/api/src/favorites/store.ts:170` 是普通可写属性，因此 `Object.assign` 能拔高它；history 同形，见 `services/api/src/history/store.ts:177`。）

**红时原文**（最终提交版本的复跑，`node` **exit 1**）：

```
REVERSE CONTROL: GY_I16_FORCE_MEMORY=1 ⇒ 装配改用内存 store（本轮的"真库行数"读数必须变红）。
Real PostgreSQL patch: 17.11
PASS 1: …
…
PASS 9: HTTP 面：real+pool 真的 201/200 落库；他人 id 与不存在同形 404
AssertionError [ERR_ASSERTION]: HTTP 新增收藏后真库 count(*) 必须 0 → 1
0 !== 1
    at file:///E:/GengYunCommander/wt-r31-i16-pg/tests/integration/favorites-history-pg.mjs:425:10
  code: 'ERR_ASSERTION',
  actual: 0,
  expected: 1,
  operator: 'strictEqual'
```

读法：**名字点出来的就是那条读数**（`HTTP 新增收藏后真库 count(*) 必须 0 → 1`），而且红在 `actual: 0 / expected: 1`——内存 store 确实回了 201、`data.id` 也有，但真库里一行都没有。前 9 组在内存装配下**仍然全绿**（`PASS 1`–`PASS 9` 九行照出），正说明这 9 组抓不住「HTTP 说有、库里没有」这类假绿（它们读的是 store 自己的返回值与 HTTP body），也说明新增的组 10 是**不可替代**的一条。

## 6. 缺口（本片**未做**，逐条说明归属）

- **F1 注释漂移（只报告不改，属业务代码）**：`services/api/src/ocr/store-pg.ts:104` 与 `services/api/src/recognitions/store-pg.ts:116` 的注释写「`favorites-history-pg.mjs` 只跑 `0001/0018`）。本次起本臂 apply `0001/0008/0018`，这句括注**数值上已过时**（结论仍成立：那三/四张表确实不在本臂库里）。红线要求不改业务代码，故本页只登记，建议下一位改这两处注释的人顺手改成 `0001/0008/0018`。
- **F2 门禁接入（非空证明不进 CI）**：反向控制开关按红线不接 workflow、不新增 workflow。若要把「装配降级必须红」变成常驻门禁，形态应是 `real-pg-integration.yml` 里**同一 job 内新增一个 step**（先建库、`GY_I16_FORCE_MEMORY=1 node …`、**期望非 0**），由指挥另派——本次不做。
- **F3 真机读数**：本页全部是 Windows 本机 17.11 回环读数。Linux runner / 容器网络 / `postgres:17.11` 服务容器的行为差异（尤其 `timezone`、`locale`、`fsync=on` 下的时序）未验；CI 侧是否有 flake 要看 PR 上 job 的运行记录。
- **F4 跨域幂等前缀互删效应**：本臂的注销读数只验证 `favorites` / `history` 两域的台账被清（`favorites_idempotency` / `history_idempotency`）。`0008` 的 `idempotency_keys` 是**另一套台账**（`scope` 是 `varchar(200)`、`key_hash` 是 `bytea`），注销时按 `scope` 前缀扫描清理的**跨域互删**效应（例如某域前缀恰好是另一域前缀的前缀，会不会误删）**本片没有覆盖**，也没有为它造读数——它是账号注销臂（`account-deletion-pg` / `#452`）的邻域，本臂刻意不重复。
