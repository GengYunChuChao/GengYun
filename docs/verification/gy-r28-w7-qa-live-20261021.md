## 4. 出口记账

### 4.1 新增 `createChatEgress`（`services/api/src/privacy/task-egress.ts`）

接口：`ChatEgress.send<T>({ userId, authEpoch, objectId, objectRevision, call, outcomeOf, failureCodeOf? })`。

派发顺序（照 `privacy/synthesis-egress.ts` 的同口径先例，`markSent` 是唯一权威授权边界）：

1. `engaged === false` ⇒ **在任何账本变更之前** 抛 `PrivacyError('PROVIDER_UNAVAILABLE', …)`：零预留、零外发。
2. `resolveRecipient`（按 `purpose='external_inference'` 绑定的接收方）。
3. `reserve({ objectType: 'conversation_turn', objectKey: 'turn:<uuid>', objectRevision, dataType: 'checked_content', purpose: 'external_inference', recipientId, sourceVersion: null })`。
4. `inFlight.assertExecutable`（执行前重查撤回/注销）。
5. `ledger.markSent(exportId)`。
6. `call()`：失败 ⇒ `markFailed(code)` 后**原样重抛**，**不**写回。
7. 成功 ⇒ `inFlight.saveResult({ …, objectVersion: sent.objectRevision, result: outcomeOf(outcome) })`。

`failureCodeOf(outcome)` 非空（例如上游「200 但被内容守卫拦下」）也走 `markFailed`，避免把一次不成立的回答记成成功外发。

### 4.2 记账内容与实际落库字段

- 账本行：`object_type='conversation_turn'`、`object_key='turn:<turn uuid>'`、`object_revision`=轮次 revision、`data_type='checked_content'`、`purpose='external_inference'`、`capability='llm'`、接收方=问答模型提供方；状态按 4.1 的时序为 `reserved → sent`（+`result`）或 `failed(error_code)`。
- **token 用量进不了账本**：`ledger-pg.ts` 的 `summarizeEgressOutcome` 只保留 `kind`（`/^[a-z_]{1,32}$/`）、`code`（`/^[A-Z_]{1,64}$/`）、`substitute`，其余字段（含 usage）一律丢弃。因此用量只进**结构化日志**（`{status, duration_ms, prompt_tokens, completion_tokens, attempts, sources, citations, model}`），并已在 §8.3 登记为「未取得」项。这是既有账本形状的约束，未擅自扩列。
- `dataType` 用的是既有闭集里唯一的非媒体成员 `checked_content`（其必需用途恰为 `external_inference`，见 `packages/privacy/constants.mjs`）；语义上「问答外发」借用了「已核查内容外发」这一维 —— **未新造 dataType**，此处如实登记为语义借用，供评审裁定。

### 4.3 为什么没有扩展 `task-egress.ts:45` 的 method 联合

`MediaJobEgress.provider()` 的形状是「包装一个长生命周期的提供者实例，`method: 'recognize' | 'transcribe'`，对象是 `media` 且带 `objectId` + `dataType` ∈ 媒体闭集」。问答外发的维度不同：对象是 `conversation_turn`、只能给 `object_key`（非媒体类型**禁止**给 `objectId`，见 `ledger-pg.ts:346-420` 的校验），而且没有可被 `provider()` 包装的实例（一次问答就是一次请求/响应）。硬把问答塞进 `provider()` 只会得到**错维度**的记账行（媒体 `object_type` + 假 `dataType`），比不记账更糟。因此新增 `ChatEgress` 而不是扩展 method 联合 —— 这是偏离派单字面要求的一处，**已由指挥裁决确认（判断正确）**，见 §8.3 第 4 条。

## 6. fail-closed 负控制（未配置 ⇒ 与 main 逐字节一致）

负控制（`tests/unit/conversation-chat-live.test.mjs`，真跑通过）：

- **负控制（未配置）：回答版本串与 main 一致，正文与确定性回答器逐字相同** —— 断言 `model_version` / `prompt_version` 仍带 `unimplemented:no-real-`，且 `answer.checked_text` 与直接调用 `createDeterministicAnswerComposer()` 的输出**逐字相等**。
- **负控制（配了模型但账本不可用）：仍走确定性回答器并留痕警告，不外发** —— 断言 `mode==='deterministic'`、警告文本命中、`lastReading`/外发计数为 0。
- **注入真实模型回答器（异步）：await 生效，引用按 `[n]` 绑定，版本串仍由装配层缺省（NC2）** —— 证明注入者不会把自己标成真实模型。
- **注入真实模型回答器：只引越界编号 ⇒ 正文不交付 ⇒ blocked**（返修前读数为 `insufficient`，返修后按 `P1` 收紧为 `blocked`，§9）—— 守卫仍是唯一降级点。

另外 4 条与门单测（①注入优先 / ②未配置 / ③账本不可用 / ④非 real）逐条固定了「不外发」的四种理由。

### 9.1 监工读数与缺陷位置（复现成立）

监工在隔离 checkout 用合成 fetch 让适配器返回 `来源[99] https://fabricated.invalid/not-in-retrieval；另见[1]。`，检索集合只有 1 条合法合成来源，得到：结构 `citations=1`、最终 `answered/passed`、正文里的 `[99]` 与集合外 URL 对用户可见。**该读数与本轮实测一致**，缺陷在 `services/api/src/ai/chat-live-adapter.ts`：`[n]` 回填循环对越界编号直接 `continue`，正文由 `clip(content, …)` 原样返回；而 `services/api/src/conversations/guard.ts` 只核结构化 `citations`/`dose_cards`，于是"悄悄丢掉越界结构 + 正文照发"能一路走到 `answered/passed`。

### 9.2 改法（三层，都在用户可见之前）

1. **适配器：正文越界 ⇒ 正文不交付**（`services/api/src/ai/chat-live-adapter.ts:122` `bodyViolationsOf`，判定点 `:328`，返回 `:366-373`）。判定两条：`[n]` 必须在 `1..used.length`；正文里出现的每个 URL 必须在本次检索集合的 `source.url` 或条目正文里出现过（`groundedUrlsOf`）。任一违规 ⇒ `{ text: '', citations, dose_cards: [], text_violations }` —— **不交付正文**，交给守卫整条阻断；日志只记条数（`text_violations`），不含正文/编号片段。
2. **守卫：正文层面越界独立复核 + 撤回引用**（`services/api/src/conversations/guard.ts:201` `urlsInText`、`:211` `groundedUrlsOf`、`:300` 收集 `rejectedText`、`:370` 未背书 URL、`:377` 参与 `blocked`、`:382-383` 正文越界时不再交付任何 citation/用量卡）。`GuardedAnswer.rejected_text` 只作判据，不进响应（响应键集仍是契约十键）。
3. **输出侧风险筛查：自由正文也要过既有硬规则**（`services/api/src/conversations/screen.ts:63` `ANSWER_RISK_BLOCK_TEXT`、`:111` 接口、`:259` 实现 `screenAnswer`；接入点 `services/api/src/conversations/service.ts:1114-1115`，在 `compose` 之后、`guard.check` 之前）。同一规则层（`DANGEROUS_MIX`/`DOSE_UNBOUNDED`/`PROMPT_INJECTION`）、同一预算与 fail-closed 口径；空正文跳过（保持"资料不足"语义，不被误标成筛查阻断）。

**为什么不是"把越界片段从正文里删掉再交付"**：删片段等于让模型用未检索内容喂出的一段话继续当回答，且删改后的正文没有任何确定性依据可核对；整条阻断+固定话术才是可审计的降级点，也与既有 `blocked` 语义一致。
