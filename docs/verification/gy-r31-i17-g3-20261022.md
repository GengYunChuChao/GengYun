## 1. 一屏结论

| # | 面 | 改前 | 改后 | 依据 |
| --- | --- | --- | --- | --- |
| a | 未读数失败后的出口 | 只把文案改成「未读数未取得：…」，pill 是纯展示、无 `bindtap`；列表成功时页面停在 `ready`，`state-view` 的 `onRetry` **根本不可达** | pill 自身就是出口：失败态渲染带 `bindtap="onRetryUnread"` 的琥珀 pill，点击**只重读未读数** | §3.1 |
| b | 失败态与「0 条」的分辨 | 只有「不显示数字」这一条不变式，失败后无路可走 | 不变式保留：失败 ⇒ `unreadText: ''`（不写 0、不保留过期值），且失败态与成功态是**互斥渲染分支** | §3.2 |
| c | 被测试固化下来的缺口 | 用例只锁定「未取得 ＋ 不显示数字」，等于把「失败即终点」固化成预期 | 同一条用例改为断言：失败标记点亮、出口是函数、模板绑定由失败态独占（**不是删断言**） | §4 |
| d | 失败不吞错 | 未读数失败**零日志**，线上只能靠用户描述 | 每次失败留一条结构化 `console.warn({ event, code })`，只这两项 | §3.3 |

一句话：**改前**未读数失败是一条死路（列表成功时连重试按钮都摸不到）；**改后**失败态自己带一个「重试」出口，只重读未读数、不整页重载、不清已读状态、连点只发一次，并且这条出口**被测试钉住**——把出口拿掉，用例立刻红并点名。

### 3.1 未读数失败后的出口（G3 主体）

| 面 | 位置 | 读数 | 判定 |

## 4. 断言订正说明（为什么不是删断言）

**原断言（改前 `tests/unit/miniprogram-ui-auth-integration.test.mjs`）**：`test('消息页：real 未接线 503 ⇒ …')` 里 `:362` `assert.match(page.data.unreadNote, /未读数未取得/)` ＋ `:363` `assert.equal(bar.data.unreadText, '', '未读数取不到 ⇒ 不显示数字（不显示 0）')`。

**如实纠一处复盘措辞**：复盘 G3 行把「被单测固化成断言」的落点写成该文件 `:362`。实读该文件，**并不存在**「断言 pill 没有 `bindtap`」「断言没有 `onRetry`」这类字面反向断言。固化的机制是**只锁终点、不锁出口**：整条用例把「文案说未取得 ＋ 不显示数字」写成了**期望的终态**，而全文件对「失败之后有没有路」零断言 —— 于是把出口补上、或把出口删掉，测试都一样绿。这比一条显式的反向断言更难发现，也是复盘说「需求被固化成现状」的真实形态。

**新断言（同一条用例原处，不删任何既有断言，只加对象）**：

| 断言 | 钉住的东西 |
| --- | --- |
| `assert.equal(page.data.unreadFailed, true, …)` | 失败必须点亮标记（它就是模板分支的开关，缺了等于没有入口） |
| `assert.equal(typeof page.onRetryUnread, 'function', …)` | 出口**真的挂在页面上**（负控制就是打掉这一条） |
| `unreadRetryTag(wxml)` 非空 ＋ `assert.match(retryTag, /wx:if="\{\{unreadFailed\}\}"/)` | 模板里的绑定由失败态**独占**，成功态渲染不出来 |
| `wxml.split('bindtap="onRetryUnread"').length - 1 === 1` | 全页只有一个未读数重试入口（不许散落多个） |
| `warns.length === 1` ＋ `Object.keys(...) === ['code','event']` ＋ 值核对 ＋ `doesNotMatch` 不许出现令牌或手机号 | 告警结构化、只两字段、不带凭据 |

为什么**不删**那条用例：它锁的两条东西（「未接线不得显示成暂无消息」「取不到不得显示 0」）是本片**必须继续成立**的不变式，删了就丢了回归护栏。订正的做法是把「终点」换成「终点 ＋ 出口」：同一个场景、同一处位置，断言对象从「现状」换成「本片新增的能力」。另外新增三条用例分别钉住成功态无出口、失败态可点且只重读未读数、连点与二次失败，缺口不再只靠一条用例兜。

## 5. 非空证明（负控制原文）

做法：**只**把 `messages.js` 的 `onRetryUnread` 方法删掉（`messages.wxml` 的 `bindtap="onRetryUnread"` 原样留着，模拟「模板接线了、页面没实现」的半接线状态），跑同一条命令；随后从备份复原再跑。

负控制（`node --test tests/unit/miniprogram-ui-auth-integration.test.mjs`，节选：四条 `✖` 标题行取自输出的 failing tests 段，各自下挂失败正文；第一条正文前的 `test at …` 行即该用例定义处的锚点）：

```

  AssertionError [ERR_ASSERTION]: 失败态必须暴露可点入口 onRetryUnread
  + actual - expected

  + 'undefined'
  - 'function'

      at TestContext.<anonymous> (file:///E:/GengYunCommander/wt-r31-i17-g3/tests/unit/miniprogram-ui-auth-integration.test.mjs:382:10)
✖ 消息页：未读数读取成功 ⇒ 成功态没有重试入口，也不把「0 条」写成 0
TypeError: page.onRetryUnread is not a function
✖ 消息页：列表成功＋未读数失败 ⇒ pill 可点重试，且只重读未读数（不整页重载、不清已读状态）

TypeError: page.onRetryUnread is not a function
ℹ tests 35
ℹ pass 31

```

复原后（同一命令）：

```
ℹ tests 35
ℹ suites 0
ℹ pass 35
ℹ fail 0
```

四条红**都点名**到具体能力：第一条是我们自己写的「失败态必须暴露可点入口 onRetryUnread」，后三条是 `TypeError: page.onRetryUnread is not a function`。也就是说，只留模板绑定、不实现页面方法，测试会红；这正是「断言重试真的接线了」而非「断言模板上有个字符串」的意义。
