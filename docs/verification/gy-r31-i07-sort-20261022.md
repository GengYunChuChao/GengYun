# GY-R31-I07 `/herbicides` 列表排序口径裁定与断言固化

2026-10-22；基线 `origin/main` `489804e4`。Refs #7，整项不关闭。

## 结论

`/herbicides` 列表「登记号升序」是**有意为之**，本版**保持现状、不改行为**。它落在 `docs/architecture/state-contract.md:32` 那一句的**第二子句**（「来源目录排序也用稳定键」），而 `(created_at DESC,id DESC)` 是同一句里的**第一子句**（管「游标列表」）——两者是并列的两件事，不是同一条排序规则。

依据：实现自带理由注释（确定性／便于分页与快照对比）、分页游标键就是登记号（排序键与游标键必须同源，否则分页会重复或漏项）、冻结实体 `Herbicide` 没有 `created_at` 故第一子句在 `/herbicides` 上**不可表达**、`/herbicides` 是 `packages/reference` 内唯一显式写比较器（且唯一被产品路由调用）的目录、既有裁定已写「目录稳定按 id／code 升序」（该口径在本仓的实现实例是 `/catalog/crops`、`/catalog/regions`，见 §4 第 4 条）。

唯一未取得：契约从未定义「来源目录」的范围（在**契约文本内**仅 `docs/architecture/state-contract.md:32` 出现过一次，无定义；契约之外另有引用与另一义用法，见 §6）。「`/herbicides` 属于它」是**本页的裁定**，不是契约逐字结论；该术语缺口转下一片，见 §6。

本页不声称 `/herbicides` 的排序符合用户期望，只声称三处现状（契约／台账／实现）各自说了什么、哪一条被满足，以及据此作出的分类裁定与它的失效条件。

## 3. 裁定

### 3.1 知识列表排序与除草剂列表排序不是同一件事

| 维度 | `/knowledge`（第一子句） | `/herbicides`（第二子句） |
| --- | --- | --- |
| 数据源 | PostgreSQL 视图 `catalog_read.current_knowledge` | 仓内参考名录（`loadHerbicideRecords()` 读 `packages/knowledge/herbicides/records-2026.json`） |
| 每行有 `created_at` | 有（0012 迁移落到表并投影，见 `services/api/src/knowledge/service.ts:73-74` 注释） | 无（实体封闭且无该字段） |
| 排序键 | `(created_at DESC, id DESC)` | `registration_number` 升序（按 UTF-16 码元比较） |
| 分页 | 服务端签名游标，绑定排序与版本水位 15 分钟 | 内存游标 = 上一页末条的 `registration_number` |
| 业务语义 | 「最近更新在前」 | 「名录按登记号翻阅」 |

### 3.2 裁定正文

`/herbicides` 列表排序 = **登记号升序**，判为**有意为之**，本版不改。它满足契约第二子句（稳定键升序），不适用第一子句（实体无 `created_at`）。不把它登记为缺陷，也不因此改动 `packages/reference/query.mjs` 的行为。

裁定带失效条件：**若架构方判定 `/herbicides` 也属「游标列表」**，本裁定立即失效、改判为缺陷；此时修复不是换一行比较器，而是契约变更（给 `Herbicide` 补 `created_at`）加行为变更，需单开一片并给前后读数。`tests/unit/gy-i07-herbicide-sort.test.mjs` 就是这道闸门：口径一变，它必红。

## 4. 依据（逐条可核，无一条出自「我觉得」）

1. **实现自己写了理由**：`packages/reference/query.mjs:512` 的注释「稳定排序：登记号升序（确定性，便于分页与快照对比）」。注释与排序代码紧邻，是显式意图而非巧合。
2. **游标键被排序键反向绑定**：`packages/reference/query.mjs:620` `list.findIndex((x) => x.registration_number === cursor)`，`packages/reference/query.mjs:625` 取本页末条的 `registration_number` 作 `next_cursor`。排序键若与游标键不同源，分页会重复或漏项，且违反 `docs/architecture/state-contract.md:32`「游标…绑定主体、过滤器、**排序**、版本水位」那半句。
3. **第一子句在此域不可表达**：`#/components/schemas/Herbicide` 封闭且无 `created_at`。实体里唯一对客户端可见的时间戳是 `source.updated_at`，在仓内 20 条记录上的直方图是 **19 条 `2026-06-04T00:00:00.000Z` + 1 条 `2026-03-26T00:00:00.000Z`**——按它排会把 19 条打成同组，组内次序由确定性 uuid 决定，与登记号语义无关，也不比登记号升序更确定。
4. **`packages/reference` 内没有「同族先例」可援引：`/herbicides` 是该包唯一显式写比较器的目录**。该包的目录读取有两条路：① `/herbicides` 走 `runQuery`，比较器显式写在 `packages/reference/query.mjs:513`（理由见第 1 条）；② 兄弟目录 `listCrops`／`listSpecies`／`listRegions` 只把**游标键选择器**交给 `paginateItems(list, limit, cursor, keyOf)`（`packages/reference/service.mjs:324-334`）——该函数**只按游标切片、不排序**（`:327` 定位游标、`:331` `slice`、`:332` 取末条键作 `next_cursor`），所以返回顺序就是目录 JSON 原序。同一 SHA 实测原序：`crops` = `crop_rice → crop_corn → crop_soybean → crop_rapeseed`，`species` = `species_barnyardgrass → species_foxtail → species_nettle_group → species_crabgrass → …`，**均非键升序**；只有 `regions`（102 条，`330000 → 330100 → 330102 → …`）恰好等于码值升序。并且这三个函数**未装配到任何产品路由**（`services/api/**` 零引用；只在 `packages/reference/service.mjs:220-222` 导出，`tests/unit/contract-planned-exemptions.test.mjs:32-33` 亦自述 `listSpecies`「产品路由未装配」）。⇒ 于是有两条并列结论：**其一**，`/herbicides` 是该包唯一显式排序、也是唯一被产品路由调用的目录（`services/api/src/routes/knowledge.ts:203`）——这是比「同一口径第三次实例」更强的事实；**其二**，本裁定不得以「同包兄弟目录已按稳定键升序」作旁证（该论据经独立审查实测不成立，已从本页删除）。「目录按稳定键升序」在本仓的真实实现实例在**另一层**：`services/api/src/routes/profile.ts:43-53` 的 `/catalog/crops`、`/catalog/regions`，排序由 SQL 给出（`services/api/src/profile/service.ts:62` `… ORDER BY id`、`:65` `… ORDER BY code`），游标令牌写 `sort: 'catalog_key_asc'`（`services/api/src/profile/pagination.ts:32` 取键字段 `id`／`code`，`:52` 校验、`:64` 写入该 `sort` 值），与 `packages/reference` 的目录函数不是同一条代码路径。
5. **既有裁定已落纸**：`docs/verification/gy-i05-api-20261011.md:24`「目录稳定按 id／code 升序，默认20／最多50…」；台账维度 `docs/architecture/contract-implementation-status.md:35`「目录按稳定键排序」。本片是**沿用**，不是新立。
6. **改判的代价与收益不对称**：改判为缺陷需要破坏性契约变更（`Herbicide` 是 `additionalProperties: false`，加字段即破坏）+ 改游标键 + 同步客户端，而可用的 `created_at` 并不存在、时间戳又退化——收益为零。
