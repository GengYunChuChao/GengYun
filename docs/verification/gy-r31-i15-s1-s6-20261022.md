## 一句话结论

两个缺口都不是「实现写错了」，而是**能力根本没接**：举报域有写入与自读两条路、没有任何「推进状态」的入口（`state` 从创建起恒为 `received`、`revision` 恒为 1），社区存储里连一个按主体清理的原语都没有（`purgeOwnerData` / `deleteAllByOwner` 在基线的 `community/store.ts` 里 **0 命中**）。本片按既有形状补齐：举报推进做成 **CAS + 三值状态机 + 409**（契约 schema 一字未动），注销按 `OwnerPurgeStore` 端口补 `community` 域（帖子/评论软删、点赞物理删、举报清自述留轨迹），并把 `community` 并入注销闭集。

## 2. S1 改法

### 2.1 状态机（照既有词汇，不自创第四态）

新增 `services/api/src/community/report-state.ts`（纯函数，不碰存储/HTTP）：

| 动作 | 合法起态 | 终态 |
| --- | --- | --- |
| `triage`（受理：举报成立，内容已隔离） | `received` | `isolated` |
| `resolve`（处置完毕结案） | `received`、`isolated` | `closed` |
| `reject`（驳回：不处置就结案） | `received` | `closed` |

- 任务书里写的 `pending → triaged → resolved|rejected` 与既有三值的对应：`pending≈received`、`triaged≈isolated`（受理即隔离目标内容）、`resolved`/`rejected` **都是** `closed`，靠**转移路径**区分（`received→closed` 是驳回，`received|isolated→closed` 是处置完毕）。
- 为什么不用第四态 `rejected`：**契约 `Report.state` 是闭枚举（`openapi.json:13796-13800`）、迁移 `0022:141` 是同值 CHECK**，加第四态必然要改契约 schema 或迁移 CHECK —— 两者都在本片禁令/高风险面内。改用「路径区分」不丢语义，也不动 schema。
- 非法转移：`closed` 出发的任何动作 ⇒ 拒（终态单向门）；`isolated` 不接受 `reject` ⇒ 拒。

### 2.2 错误码：**409 + 既有封套**，并记「新口径，待裁」

- 既有约定在 `docs/architecture/state-contract.md:23`：`409 = REVISION_CONFLICT / IDEMPOTENCY_CONFLICT / OBJECT_UNAVAILABLE`——**没有** `STATE_CONFLICT` 这类码。
- 本片因此用 `409 REVISION_CONFLICT`（`services/api/src/community/service.ts:1462-1465`）承载「终态后不可再处置 / 非法转移」，与既有 `commitRefusal()`（`service.ts:446`、`:450`）同码同封套。
- **这是新口径，待裁**：语义上「状态不接受该动作」与「版本不匹配」并不等价；本片选择复用既有码而不新增码，因为新增错误码要动契约错误枚举（禁令）。建议裁定：是否在下一片把 `STATE_CONFLICT` 正式写进契约 409 闭集。

### 2.3 幂等：由 CAS 承载，不新造键

- 新增 `commitReportIfCurrent(id, expected, patch)`（`store.ts:257` 接口 / `:522` 内存实现 / `store-pg.ts` 的 `commitReport()`），判定顺序与 `commitPostIfCurrent` **逐条一致**：`NOT_FOUND → REVISION_CHANGED → STATE_CHANGED`；PG 侧 `SELECT ... FOR UPDATE` 后同序判定。
- 重复处置：拿同一个 `expected_revision` 再调一次 ⇒ 第一次已经把 revision 推高 ⇒ 第二次 `REVISION_CHANGED` ⇒ **409**，不静默成功、不产生第二条记录。
- `Idempotency-Key` 那条线**没动**：`createReport` 的既有幂等语义（同键重放返回同一举报 id）由 `withIdempotency` 原样保留，并被用例钉住（`tests/unit/community-report-disposition.test.mjs` 的「既有幂等语义如实保留」一条，改前改后都 PASS）。
- **同一用户对同一对象重复举报**：读实现 ⇒ 既有语义是「**允许**重复举报，不建 `(reporter_id,target)` 唯一约束」，理由写在 `0022_community_persistence.sql:120-124`（去重由 `Idempotency-Key` 裁决，加唯一键会把「换个 key 再举报」从两行变成 503，与内存实现语义不同），并有 `tests/integration/community-pg.mjs:366-372` 的既有断言。本片**不改变**这条语义（任务书说「按既有幂等语义处理，别自创」）。

### 2.4 不改契约的做法

- 服务层新增 `advanceReport(reportId, { action, expected_revision })`（`service.ts:1455-1474`），入参校验在 `validate.ts`（`validateReportDispositionInput`，未知字段/动作闭集/正整数版本）。
- **不注册任何路由**：契约没有处置 op，注册路由会让 `contract-status` 类静态门禁与「路由↔契约一一对应」的既有约定打架。已接线的是能力，不是入口（见 §8 未取得项第 1 条）。

## 4. S6 改法 + 判断依据

### 4.1 判断依据：为什么是「软删 + 清自述」，不是硬删

三类数据分开判，判据都是**读既有代码得到的先例**，不是猜：

1. **帖子/评论 ⇒ 软删（`visibility='deleted'` + `revision+1`）。**
   - 硬删会拆到别人：`community_comments.post_id` 是 `ON DELETE CASCADE`（`0022:100`），删一条帖子会连**别人**在下面的评论一起带走；`community_likes` 的 `(target_type,target_id)` **没有外键**，硬删内容会留下指向不存在目标的点赞行（悬挂引用）。
   - 既有先例：作者删除内容本来就是 `visibility='deleted'`（`deletePost`/`deleteComment` 走 `commitXIfCurrent` 写 visibility），注销复用同一条路，不发明第二种「消失」。
   - `revision+1`：旧 ETag 一律 409，避免「内容已消失但读者以为还看得见」。
2. **点赞 ⇒ 物理删。** 集合语义、无历史价值，且留着等于保留「该用户点过哪些帖」的行为痕迹，与注销目的相反；表级 DELETE 授权已存在（`deploy/postgres-cvm/sql/20-login-roles.sql:551`）。
3. **举报 ⇒ 只清 `detail`（自由文本），行与 `state` 保留。** `detail` 是这一行里唯一的自由文本 PII 面（`reason_code` 是闭集 CHECK）；行必须留，因为运营正在处置的举报一旦物理删除，被处置的内容就失去依据，且处置轨迹是审核域的留痕。与既有 `messages` 域「清正文、留骨架」同口径。

### 4.2 改动

- `community/store.ts:443` 接口新增**可选** `purgeOwnerData?(ownerId): Promise<CommunityOwnerPurgeCounts>`（`{records, idempotency}`，与 privacy 的 `OwnerPurgeCounts` 逐字段一致）；内存实现 `:737`。
- `community/store-pg.ts`：`purgeOwnerData` 在 `withTransaction` 里 5 条语句（posts/comments 软删、reports 清 detail、likes 物理删、`DELETE FROM community_idempotency WHERE scope LIKE '<ownerId>\n%'`）。**没有新建迁移、没有改任何 GRANT**：用到的列全在既有列级授权清单里（`20-login-roles.sql:481-493` posts、`:496-501` comments、`:514-523` reports、`:511` likes 表级 DELETE、`:548` idempotency 表级 DELETE）。
- `services/api/src/privacy/user-data-deletion.ts`：新增 `COMMUNITY_DELETION_MODULE = 'community'`（`:106`），deps 新增可选 `communityStore?: OwnerPurgeStore`（`:256`），注册点 `:505-510`（注入才注册）。
- `services/api/src/app.ts:1668` 起：`createCommunityOwnerPurgePort()` 把社区 store 的 `purgeOwnerData` 收窄成注销端口；`:1698-1703` **无条件注入** `communityStore`，所以真实注销路径一定清社区行。

### 4.3 闭集折中（必读，含代价）

进常量闭集（`USER_DATA_DELETION_MODULES`）会让 `requiredModules()` 恒为 5，直接推翻 4 个测试文件里 **14 条**钉死「四域、不多不少」的既有断言，并要给 7 个文件里 **44 处**替身补字段 —— 那是一次独立的扩集动作。本片因此改成「**装配处补齐闭集**」：注入社区清理原语时把 `community` 追加进闭集（`user-data-deletion.ts:329-334`），既有替身不注入 ⇒ 闭集仍是 4 项 ⇒ 既有断言逐条不动；`app.ts` 无条件注入 ⇒ 生产路径闭集是 5 项。

**代价（已知弱化）**：哪天有人装配时漏注入社区 store，闭集会**静默**回到 4 项、不会有「缺模块」提示。这是本片最该被裁的一点，见 §9 第 2 条。

## 8. 未取得项（如实登记）

1. **举报处置没有 HTTP 入口**：受「不改契约 paths」约束，`advanceReport` 只到服务层，没有路由、没有 operationId。真正的运营队列/处置入口要等契约补一条 op（下一片）。
2. **处置方的身份与权限未建模**：`advanceReport` 目前不做归属校验（举报者能读不能推），谁能调由进程内调用方决定；没有接管理员会话/角色校验，也就没有越权用例。
3. **处置轨迹没有落库字段**：谁在什么时候处置的、处置结论文本，都没有列可存（要新增内部列 + 迁移 `0028`）。本片只推进 `state`/`revision`。
4. **PG 臂未在本机取得真库读数**（§6）：本机无 PG 17，断言按既有语句风格与列级授权清单逐列核对，须在 CI 首次运行确认。
5. **备份副本清单不含社区域**：`backupCopySources()` 全有或全无，社区 store 没有 `snapshotOwner`，加进去会让整份清单变 null、连锁打断 GY-I19 既有行为 —— 因此社区行的备份清除态如实 `pending`。
6. **注销闭集是「装配处补齐」而非常量扩集**（§4.3）：漏注入会静默回到 4 项。

## 9. 需要指挥裁定的点（3 条）

1. **409 码的语义复用**：非法转移/终态再处置复用 `REVISION_CONFLICT`（既有闭集，不动契约）；是否在下一片把 `STATE_CONFLICT` 正式加进契约 409 闭集？
2. **注销闭集的扩集方式**：本片取「注入才追加 → 既有 14 条断言与 44 处替身零改动」，代价是漏注入会静默退回 4 域。要不要改为「常量闭集直接加 `community` + 一次性改写既有断言/替身」（更强，但那是独立的、更大的改动）？
3. **重复举报去重**：既有语义是「同人同对象可重复举报，不建唯一约束，靠 `Idempotency-Key` 裁决」，并写着「重复举报是产品问题，不是数据完整性问题」（`0022:120-124`、`community-pg.mjs:366-372`）。本片照旧未改；如果产品口径要求「同人同对象只能有一条待处置举报」，那是一次明确的产品+存储改动，需要裁定后再做。
