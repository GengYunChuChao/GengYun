## 0. 结论（一句话，可判真假）

> 共享台账 `public.idempotency_keys` 的 `scope` 首段**恒为主体 uuid**（`idempotencyScope` 拼 `<主体>\n<METHOD>\n<路径>`），注销清理按 `left(scope, char_length($1::text) + 1) = $1::text || chr(10)` 做**精确前缀比较**，且全仓不存在 `msg:` / `ocr:` / `recognition:` / `conversation:` 这类域标签前缀 ⇒ **不存在「删本域台账误删他域」的跨域误删**；真实存在的跨域效果是同主体在 auth / profile / privacy 写入的幂等行被**一并删除**，性质是**主体级连坐**（已被 `tests/integration/messages-purge-pg.mjs` 的 CI 真库臂断言为「必须发生」）；该性质依赖两条承重前提——① 主体恒为 `uuid`（不含分隔符）② 分隔符只有一处定义——任一被破坏，前缀删就不再表达「本主体的行」。

因此本片**判定不改生产语义**，只把上述前提「收敛到一处 + 钉成守卫 + 配负控制」（§5）。

## 2. 实测 b：注销链路是「主体前缀**精确**删」，不是 `LIKE 'msg:%'`，也不是按行删

`services/api/src/messages/store-pg.ts:220-241`（读原文）：

```ts
  async function purgeOwnerRows(ownerId: string): Promise<MessagesOwnerPurgeCounts> {
    const transactional = asTransactionalPool(pool);
    if (transactional === null) {
      // 两表删除必须同生共死：拿不到事务连接就如实不可用，不退回"两条独立语句"。
      throw new ApiError('PROVIDER_UNAVAILABLE', '消息域注销清理需要事务连接，当前数据库池不提供', {
        retryable: false,
      });
    }
    return withTransaction(transactional, async (sql) => {
      const records = await sql.query(
        'DELETE FROM public.messages WHERE owner_id = $1::uuid RETURNING id',
        [ownerId],
      );
      const idempotency = await sql.query(
        `DELETE FROM public.idempotency_keys
          WHERE left(scope, char_length($1::text) + 1) = $1::text || chr(10)
          RETURNING scope`,
        [ownerId],
      );
      return { records: records.rows.length, idempotency: idempotency.rows.length };
    });
  }
```

判据与读数：

- **不是 `LIKE`**：谓词是 `left(scope, char_length($1::text) + 1) = $1::text || chr(10)`，**逐字符相等**；`_` / `%` 不会被当通配符（`:207-211` 注释：「`left(...) = $1::text || chr(10)` 不解释通配符（`_`/`%` 不会走样）」）。
- **不是按行删**：值只有一个 `[ownerId]`，行数取自两条 `RETURNING` 的**实际行数**（`:204-205`「两个行数都取自 `RETURNING` 的**实际返回行数**（`SqlRunner` 没有 `rowCount`），因此证据里的 `messages:online-purged:<n>` 是『真删了 n 行』」）。
- **事务同生共死**：`BEGIN` → `SET LOCAL lock_timeout = '4s'` → 两条 DELETE → `COMMIT`，异常 `ROLLBACK`（`:96`、`:107-115`）。

内存实现同义：`services/api/src/messages/store.ts:255-273`，改前 `const scopePrefix = \`${ownerId}\\n\``，用 `key.slice(0, boundary).startsWith(scopePrefix)` 对 `<scope>\u0000<keyHash>` 复合键判断。

### 2.1 前缀是否可能与其它域相撞 —— 逐条比对

| 问题 | 读数 | 结论 |
| --- | --- | --- |
| 前缀是什么 | `<主体 uuid>` + `chr(10)` | 36 字符定长 + 单个换行 |
| 主体里会有换行吗 | `0001_initial_schema.sql:33` `id uuid PRIMARY KEY DEFAULT gen_random_uuid()` | **不会**（`uuid` 形态不含分隔符） |
| 别的域用同一张表同一语法吗 | §1.3 五域**全部**经 `idempotencyScope` | 是同一语法，所以首段也是各自主体 |
| 会不会把别的**主体**的行带进来 | 实测诱饵 `${uuid}0`／`${uuid}-`／35 位截断／前后空格 | **零命中**（前缀多/少一个字符都不相等） |
| 会不会把同一主体的**别的域**的行带进来 | **会，且这是设计内的** | 见下 |

`:213-215` 注释逐字（改前改后一致，本片未改这段）：

```text
   * ⚠️ 需要接线的决策者知情的一处**跨域**效果：因为是共享表，这条前缀删会连带删掉本主体在
   * **其它域**（如 auth 登录/登出）写入的幂等行。它们本属被注销主体、`outcome` 里也可能引用
   * 该主体的资源，删除与注销语义一致；但它**不是**本域独占的表，属副作用而非本域自清。
```

⇒ G5 说的「跨域副作用」**真实存在**，但性质是**主体级连坐**（同主体的行本来就不该在被注销后留下），**不是**「域前缀误删到别人头上」。唯一真实风险面是并发：正好在删除瞬间有本主体**他域**请求处于「占位中」（`outcome IS NULL`），它的占位行会被删掉——该风险已被上述注释显式知情，且不属于「误删他人数据」。

## 4. 判定：不改生产语义

依据（三条，缺一条这个判定就不成立）：

1. **删的每一行都属于被注销主体**：前缀首段 = 主体 uuid，`uuid` 定长且不含分隔符 ⇒ 不存在「A 的前缀命中 B 的行」；
2. **跨域连坐是注销语义的正确结果而非缺陷**：共享表里的行 `outcome` 里可能就是该主体资源的回执，主体被注销后保留它既无意义也不合规；这条已由 `tests/integration/messages-purge-pg.mjs` 在真实 PG 上**断言必须发生**（`M` 必须包含他域行）；
3. **改跑法的风险大于收益**：要避免连坐只能给表加 `domain` 列（要迁移 + 回填 + 改 5 个域 + 改唯一键），而派单红线是「不新增迁移」。本片判定**不改**，把「连坐要不要变成显式的 `domain` 分区」留给决策者（§8 裁定点 2）。

⇒ 处置：**不加迁移、不改 SQL 文本、不改语义**，只做「前缀单点化 + 结构性守卫 + 负控制」。
