## 2 本条臂的覆盖清单

文件：`tests/integration/messages-pg.mjs`（`1 file changed, 217 insertions(+), 2 deletions(-)`）。本片在既有 7 节（`[M]`/`[D]`/`[R]`/`[N]`/`[C]`/`[U]`/`[P]`）之上做了两类改动：

**(a) 把「列表 + 未读计数 + 标记已读」的一致性从「三次恰好相等」升级成「同一快照口径」**

- 同一连接、`BEGIN ISOLATION LEVEL REPEATABLE READ`，**一条 SQL** 同时取 `count(*)::int AS rows` 与 `count(*) FILTER (WHERE read_at IS NULL)::int AS unread`，同事务内再取逐行 `read_at`，`COMMIT`；
- 断言：聚合行数 == 逐行行数；事务内 `unread` == 事务外逐行统计 == HTTP `GET /messages/unread-count` 的 `data.count`；
- 断言 `information_schema.columns` 里 `messages` **不存在**任何 `ILIKE '%unread%'` 或 `'%count%'` 的列 ⇒ 未读数是派生量，不是计数器列；
- 并发两次（本片用 20 并发）标记已读：`200×1 / 409×19`，`revision` 终值 2 ⇒ **版本只推进一次**。

**(b) 新增 `[X]` 注销即删消息一节（G4 本体，8 条断言）**

1. A 的消息行被**硬删**：`count(*) WHERE owner_id = A` 从 9 变 0；
2. 不误删他人：B 的消息 id 序列 `deepEqual` 注销前基线（2 条逐 id 原样）；
3. 同主体跨域同批清空：A 的 `favorites` 2→0、`history` 2→0；B 的 1/2 逐 id 原样；
4. 幂等台账按主体前缀清：A 前缀行 3→0，B 的 0 行原样（判据与 `purgeOwnerData` 同口径 `left(scope, char_length($1)+1) = $1 || chr(10)`）；
5. 硬删而非软删：`messages` 仍是 8 列，且列名过滤 `/deleted|is_deleted|state|status/i` 为空；
6. 只清域数据不删账号：`public.users` 里 A 的 1 行仍在（⇒ 不是外键级联的副作用）；
7. 证据串 `messages:online-purged:<n>;messages:idempotency-purged:<m>` 的两组数字分别等于 9 与注销前台账读数；回执 `handlers` 里 `messages.online_state === 'completed'`，`backup_state ∈ {pending, completed, blocked}`；
8. HTTP 反向控制：注销后用 B 的 token 打 `GET /messages` 仍 `200` 且 2 条 ⇒ A 的注销不波及他人会话。

走的是**线上装配那条路**，脚本自己**不拼 DELETE**：`buildApp` 里 `messagesDeletionStore`（`services/api/src/app.ts:1994-2012`（原记 `:1853-1871` → `:1499-1521`））包住的正是 `:867-872` 建、`:877-893` 交给 `messagesService` 的同一个 `messagesStore`，由 `createUserDataDeletion`（`:1518-1551`）按模块闭集调用。收藏/历史在这份装配里也是**真库 store**（`:1337-1346`，有池即 PG 实现）——这正是本条臂比 `messages-purge-pg.mjs` 更进一步的地方：后者那两条用的是**内存** store。

口径如实说明（写在脚本注释里）：收藏闭集只有 `species|herbicide|scheme`、历史来自识别/OCR 任务，所以三个域的行**不指向同一个对象**（A 的消息指向 `post`）。本节量的是「同主体跨域共存时，注销只删本主体、消息行真被硬删、行数进证据」，**不是**「收藏能引用消息」。
