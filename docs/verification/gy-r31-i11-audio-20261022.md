# #11「音频解码 MP3→WAV 未实现」：先证再定

日期：2026-10-22，Asia/Shanghai。基线：`origin/main` = `a02c6e48`（本页行号在该提交实测；工作树 `wt-r31-i11-audio`，分支 `feat/gy-r31-i11-audio`）。
工具链实测：`node v24.16.0`、`npm ci --prefer-offline --no-audit --no-fund --ignore-scripts` 退出码 0。

本页只回答一件事：**MP3 能不能进、进来以后怎么样了、谁在拒绝、契约到底要不要它**。
结论是**判定页**：本版**不改业务行为**，只补结构性守卫 + 登记 planned（裁定 **(c)**，理由见 §5）。

## 0 结论先行

1. **上传侧是收 MP3 的**：契约 `UploadInput.mime` 含 `audio/mpeg`（`packages/contracts/openapi.json:12953`），
   代码白名单也含它（`packages/media/constants.mjs:48`），而且 MP3 的**真实时长**是逐帧算出来的
   （`packages/media/audio.mjs:165-199` `mpegDurationMs`）⇒ MP3 能一路拿到 `media_id`。
2. **转写侧一律不收 MP3**：真实 ASR 适配器只认 16kHz/单声道/16bit PCM WAV
   （`services/api/src/ai/asr-live-adapter.ts:81-124` `requireLiveAsrWav`），MP3 在 `:89-91` 就被拒，
   **零发包、零预留、不产出文本**。拒绝文案本身是点名的：
   `录音 WAV 不合法：RIFF/WAVE 头或长度不一致（不裁剪、不转码，fail-closed 未发包）`（`:87`）。
3. **但客户端看到的不是那句文案。** `:178-181` 的裸 `catch` 把上面那个具体错误压成
   `{ kind: 'failed', code: 'PROVIDER_UNAVAILABLE' }`——而它自己的注释写着
   「取不到/音频不合法：不打供应商，**也不把它说成供应商故障**」（`:179`）。
   注释与返回值自相矛盾。作业落 `failed` + `error_code=PROVIDER_UNAVAILABLE`，无转写记录，
   `GET /speech/transcriptions/{id}` 直接 404 ⇒ 用户永远看不到「请上传 WAV」。
4. **没有任何可用的解码器**：依赖树、`node_modules`、运行环境 PATH 三处都没有
   `ffmpeg` / `ffprobe` / `fluent-ffmpeg` / `wav-decoder` / `music-metadata` / `web-audio-api` / 任何 waveform 库（§3 给了命令与结果）。
   仓内只有「时长解析」，没有「PCM 解码」——这两件事常被混为一谈，本页 §3 分开写。

## 2 事实二：现在收到 MP3，会发生什么

### 2.1 上传能过（所以缺口不可能被「上传就拦住」掩盖）

`packages/media/validate.mjs:123-189` `assertBytesMatchDeclaration` 对音频分支强制用**字节**算真实时长
（`:167` `computeAudioDurationMs(bytes)`），算不出就受控拒绝（`:169-171`
`无法从字节验证音频真实时长` / `duration_unverifiable`）。MP3 走得通：`packages/media/audio.mjs:165-199`
的 `mpegDurationMs` 跳过 ID3v2 后逐帧累计 `samplesPerFrame`（`:168-174`、`:179-198`）。
实测见 §7 的用例 A：5 帧 44100Hz ⇒ 真实时长 131ms，`voice_question` 校验放行。

### 2.2 转写受理：202，然后异步失败

| 跳 | 位置 | 行为 |
| --- | --- | --- |
| ① 路由 | `services/api/src/routes/speech.ts:161-195`；`:187-189` 注释「202：已受理、尚未完成」+ `.status(202)` | `POST /api/v1/speech/transcriptions` ⇒ **202 `JobEnvelope`**（受理体只有 `media_id` + `revision`，`MEDIA_JOB_INPUT_SCHEMA` 在 `:64`） |
| ② 作业执行 | `services/api/src/speech/service.ts:518-548` `execute`；`:598-621` `runProviderWithDeadline` | 取作业 → 调 `provider.transcribe()` → 按 `kind` 落终态 |
| ③ 真实适配器 | `services/api/src/ai/asr-live-adapter.ts:172-181` | 见下 |
| ④ 终态 | `services/api/src/speech/service.ts:541-545`：`commitTerminal(jobId, running, { state: stateForProviderFailure(value.code), errorCode: value.code }, null)`（映射函数 `:251` `stateForProviderFailure`） | 作业 `failed`，`error_code=PROVIDER_UNAVAILABLE`；**不写 TranscriptionRow**（`:596` 只有 succeeded 才写）⇒ `GET /speech/transcriptions/{id}` = 404 `NOT_FOUND` |

`services/api/src/ai/asr-live-adapter.ts:176-181` 原文：

```
const raw = await audioSource.read({ jobId, mediaId, mediaRevision });
audio = requireLiveAsrWav(raw, profile);
} catch {
  // 取不到/音频不合法：不打供应商，也不把它说成供应商故障。
```

具体拒绝原因在 `requireLiveAsrWav`（`services/api/src/ai/asr-live-adapter.ts:81-124`）：
MP3 命中 `:89-91` 的 `RIFF`/`WAVE` 与长度一致性判定，`:87` 抛出

```
AsrLocalInputError('OBJECT_UNAVAILABLE',
  `录音 WAV 不合法：${label}（不裁剪、不转码，fail-closed 未发包）`)
```

⇒ 线上可观测的三件事全部是**好的**：**不发包**（0 次 `fetch`）、**不预留预算**（0 次 `gate.reserve`）、
**不产生任何文本**（绝不把 MP3 字节当 WAV 发出去，也不猜内容）。
唯二**不好**的：**错误码错**（格式问题显示成供应商故障）、**客户端话术缺失**（202 受理后静默 failed，拿不到格式要求）。

### 2.3 为什么现在做不到「受理期就 400」

受理体是 `{ media_id, revision }`（`services/api/src/routes/speech.ts:64`），而媒体端口
`services/api/src/speech/media.ts` 的 `MediaResolution` 只回 `{ ok: true, revision }` ——
**回执里没有 mime、没有字节**。⇒ 要在受理期判格式，必须改端口形状（见 §8 补丁 ①）。
这不是文案问题，是装配层面的能力缺失。

## 5 裁定：选 (c)，并说明为什么 (a)/(b) 都不成立

**裁定：(c) 判定超出本版范围** —— 不改业务行为，缺口登记为 `planned`，并补结构性守卫（§6）。

- **(a) 不选，因为它的前提是假的。** (a) 要求「契约允许不支持」并且「文档里写着仅 WAV」。
  实际上 openapi 的 `UploadInput.mime` **至今含 `audio/mpeg`**（`packages/contracts/openapi.json:12953`），
  上传侧代码也放行 MP3。合同并没写"仅 WAV"。按 (a) 去做，就要么改契约（本版禁止），
  要么把一个契约允许的上传类型说成"契约不允许"，两种都是撒谎。
- **(b) 不选，因为契约没有「要求支持 MP3」。** 转写侧契约（冻结档位）要求的是 **WAV**；
  MP3 → WAV 是**实现选择**，不是契约义务。而且真正的最小实现绕不开解码器：
  纯 JS 的 MP3→PCM 需要完整的 Huffman 解量化 + IMDCT + 重采样（数千行、无可复用件），
  运行环境也没有 ffmpeg 二进制。任务书明写「若必须引依赖，先停下来报告，不要自行加 dependency」
  ⇒ 本片**不引依赖**，把选择权交回指挥（§8 给了三条可选路径与取舍）。
- **(c) 与文本相符**：`state-contract.md:43` 自己就写着「候选格式」「仍待 GY-I25 验证」，
  说明录制格式当时**就没定死**。在这样的文本下标一个既有 fail-closed 的缺口为 planned，
  是唯一不需要改契约语义、也不需要假装支持 的动作。

**副产品（已结晶成断言）**：拒绝路径虽然码不对、话术缺，但**行为是安全的**
（零发包 / 零预留 / 不伪造文本 / 不静默截断）。本片把它冻成守卫，避免后续"顺手转码"或"顺手放过"。

## 8 解除条件与三条可选补丁（需裁定，本版均未做）

**解除条件**（任一满足即可把两条 `todo` 转正式断言并结案）：

1. 客户端改录 **WAV**（16kHz/单声道/16bit）—— 服务端零改动即可转写。最小成本，也最符合现有契约。
2. 批准**引入解码能力**（ffmpeg 二进制或 npm/WASM 解码器）—— 走 (b)，在媒体域完成 MP3→16k mono WAV。
3. 换**支持 mp3 的 ASR 接口** —— 属改契约（openapi 语义 + 冻结档位），不在本片范围。

**补丁 ①（话术，最小）**：让 `AsrLocalInputError.code` 不再被裸 `catch` 抹平。
`services/api/src/ai/asr-live-adapter.ts:178-181` 改成区分 `AsrLocalInputError`（本地格式/字节问题）与其他异常，
把 `INVALID_REQUEST` / `OBJECT_UNAVAILABLE` 透传出去；作业就带得出可读原因。**仍需**作业→响应的话术映射。

**补丁 ②（受理期 4xx，正路但动端口）**：`SpeechMediaPort.resolve` 回 `{ ok:true, revision, mime }`，
路由在受理期就能对 `audio/mpeg` 回 400/415 并点名 WAV。⚠ 这是端口形状变更，会影响 `speech/media.ts`
的四个实现（substitute/unwired/http），需指挥裁定。

**补丁 ③（错误码语义）**：`error_code` 增格式类码（如 `MEDIA_FORMAT_UNSUPPORTED`），
需同步 `ErrorCode` 闭集 + openapi 枚举 + 前端文案。⛔ 本版禁止（不改 openapi 字段语义）。
