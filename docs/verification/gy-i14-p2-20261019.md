## 1 复核现状（逐条：先确认缺口真的存在）

### 1.1 P2-1 下架事件的 revision 口径差 1，且事件零订阅方（诊断 R5 / R6）

同一次后台下架，两条路径给出**不同版本**：

| 路径 | 取值 | 语义 |
| --- | --- | --- |
| `services/api/src/app.ts` 的 `withModerationTakedownLink` | `before.revision`（`getPost` 在 `hidePost` 之前读到） | **处置前**：被公开发布、被读取缓存、审核域 `cache.invalidateTarget` 键住的那一版 |
| `services/api/src/community/takedown.ts` 的社区事件 | `result.record.revision` | **处置后**：`hide()` 的 CAS 补丁是 `revision: current.revision + 1`，所以它恒为处置前 +1 |

复核证据：`services/api/src/admin/ops/community-posts.ts` 的 `hide()` 提交
`{revision: current.revision + 1, visibility: 'hidden'}`，且 CAS 的 `expected.revision` 就是处置前版本 ⇒ CAS 成功本身证明
`expected.revision === 提交前当前版本`。而 `result.record.revision` 已经是 +1 之后的值。

同时 `services/api/src/moderation/service.ts` 的 `withdraw()` 返回体里带一个
`event: { kind: 'moderation.takedown', … }`，**全仓零订阅方**：生产装配没有任何消费者，`invalidated_cache_keys`
才是真正被消费的信号（社区 `moderation-link.ts` 与 HTTP 层都只看它）。⇒ 事件留着"看起来接上了"，实际一旦有人接，
按事件里的版本去失效缓存/核对版本，**恰好失效不到真正被缓存的那一版**（R6 描述的失效键打错版本）。

### 1.2 P2-2 版本前进只置 `pending`、不触发重评，读面仍把旧结论当"已审"（诊断 4-3 / R4）

- 社区侧只有**community 自己的规则集版本**会让结论 stale（`community/service.ts` 的 `effectiveState` 走 `gate.assess`）；
  审核域的**模型 / prompt / 规则**版本前进，社区读面完全感知不到。
- 审核域读面 `readView` 的顺序是 `checkReadVisibility`（可见性、`current_revision`、`published_revision`、作者状态）→ 缓存；
  **全程不读任何 rule/model/prompt 版本**。
- 社区侧判定 `moderation-link.ts` 的 `judgeTasks` 只读 `decision` / `hard_rule_passed` / `reason_codes` / `provider`，
  **不读版本字段** ⇒ 结论过期了也照样 `publishable = decision === 'approved'`。
- 结论：已公开内容在源版本前进后，读面仍按"已审"返回，直到有人手工重评。诊断 4-3 的"只置 pending"指的就是这条断链。

### 1.3 P2-3 空断言（诊断 R4 / P2-7）

- `services/api/src/moderation/nonbypass.ts`：`export function assertSourceUnchanged(before, after) { return before === after; }`
  **零生产调用**（`git grep -n assertSourceUnchanged` 只命中定义处与一处文档登记），它只能证明"同一变量等于自己"。
- 同文件 `humanReviewQueue()`：`voting: PUBLIC_VOTE_ENABLED ? 'disabled' : 'disabled'` —— 两个分支同值，翻转常量不会有任何反应。
- 测试侧对"AI 不改来源"的断言是"筛查前后 `source_kind` 相同"，但从不调用上面那个函数 ⇒ 恒真断言被当成证据。

## 2 改法（每条：改了什么 + 为什么这么选）

### 2.1 P2-1：**删掉死事件**，把口径统一到"被下架的那一版"

选择"删事件"而不是"接消费者"，理由：

1. 真实信号已经存在且**同步完成**：`withdraw()` 内部就 `cache.invalidateTarget(target)` 并把真正清掉的键返回，
   接一条异步事件只会多一个"事件丢了但缓存没清"的失败面。
2. 事件若接消费者，唯一合理用途就是失效缓存/通知；而它此前零消费者，接上等于**新造一条投递链**（含重试、去重、幂等），
   属于新功能而非缺口修补，超出 P2 范围。
3. 社区侧**确实有**消费者（消息中心 `messages.appendMessage`，`event_key = community:takedown:…`），那条通知的
   `target_ref.revision` 才是对外可见的版本 —— 它必须与缓存键同口径，所以口径统一到 `expected.revision`。

改动：

- `services/api/src/community/takedown.ts`：事件 `target.revision` 改取 `expected.revision`，文件头新增
  「## 事件版本口径（与审核域下架键**同一套**）」说明（含 R6 的理由）。
- `services/api/src/moderation/service.ts`：`WithdrawOutcome` 删 `event` 字段；`withdraw()` 只返回
  `{target_ref, visibility:'hidden', withdrawn:true, invalidated_cache_keys}`，并注明"失效在同一次调用内同步完成"。
- `services/api/src/community/moderation-link.ts`：`LinkWithdrawResult` 删 `event`，`withdraw()` 删掉整段 event 映射。
- `docs/moderation/http-layer.md`：下架段与 §9 示例去掉事件，只留 `invalidated_cache_keys`。

### 2.2 P2-2：结论新鲜度**实时派生**，读面不得把过期结论当已审；状态仍用既有字段

不新增契约状态（`packages/contracts` 未动）：

- 任务视图加两个**内部**字段：`stale: boolean`、`stale_reason_codes: string[]`（`ModerationTaskView`，不进 HTTP 契约；
  作业响应由 `job-source.ts` 逐字段重建，不会泄漏）。
- `service.ts` 新增 `versionFreshnessOf(task)`：复用引擎的 `evaluateModelReReview`（与 `reReview()` 同一套判定），
  **不带 `input`**，并过滤 `MODEL_LAYER_INPUT_BINDING_UNVERIFIED` 与 `NOT_PUBLISHABLE` —— 读面拿不到正文，
  照抄会把"内容摘要未核验"误报成"版本过期"，那样所有已发布内容都会永久不可见。
- `readView()` 在 `checkReadVisibility` 之后加闸门：已发布但存在 stale 任务 ⇒ `visible:false`、
  原因码 `['RESCREEN_REQUIRED', ...stale 原因码]`、并清掉缓存（缓存只知道可见性，不知道新鲜度这一维）。
- 社区侧 `moderation-link.ts`：`readTasks` 读 `stale`（**缺字段按过期处理**，fail-closed），
  `judgeTasks` 把"approved 但 stale"归到既有契约状态 **`pending`**（既不驳回也不算通过），
  社区读面既有的 `domainWithholdingOf` ⇒ `demoted('pending')` 自动把它退成 `hidden + pending`，**社区代码不用改**。
- `RESCREEN_REQUIRED` 只进内部可见性原因码数组 `VISIBILITY_REASON_CODES`，不是契约错误码，openapi 闭集未动。

"待重评"的表达方式：对用户就是既有的 `audit_state: 'pending'`（列表里消失、公开读 404、作者视角 hidden/pending）；
对内部可观测面是 `stale`/`RESCREEN_REQUIRED` + 引擎既有 `*_VERSION_CHANGED` / `*_UNKNOWN` 原因码。

### 2.3 P2-3：删死函数，把"不改来源"换成**结构性**判据，把假三元换成真分支

- 删除 `assertSourceUnchanged`；模块头第 2 条红线改写为结构性口径：**内容权威端口 `ContentAuthorityPort` 根本没有写来源的方法**，
  只有 `setVisibility` / `setPublishedRevision`（`services/api/src/community/moderation-authority.ts`），
  "审核前后来源一致"由"没有可写入口"保证，而不是靠一个恒为 `true` 的函数。
- 测试把判据落在**键集**上：`Object.keys(authority)` 必须恰为
  `['origin','publishedRevision','read','setPublishedRevision','setVisibility']`，且没有任何 `/source/i` 的键。
  谁给权威端口加一个写来源的方法，断言立刻红。
- `humanReviewQueue()` 改成两臂真不同：`voting: votingEnabled ? 'enabled' : 'disabled'`，`votingEnabled` 默认取唯一事实源
  `PUBLIC_VOTE_ENABLED`；可选入参 `assumptions.public_vote_enabled` **只是测试缝**（生产调用方不传），
  用来断言另一臂 —— 否则常量恒 `false` 时"两臂同值"这种写法根本测不出来。
