## 3 三处高风险必查

### ① 是否真调供应商，还是硬规则兜底？——**答案：真实供应商零外呼，等价于「规则层真跑 + 模型层硬缺省」**

- real 模式装配点把端口表清空并声明 fail-closed：`services/api/src/moderation/provider.ts:109-113`
  > `return { execution_mode: 'real', ports: {}, substitutes: [], fail_closed: true };`
  同处注释写明「真实端口必须由真实适配器 + 一次显式、可审查的接线变更提供（本阶段不存在这样的适配器）」。
- 服务装配点据此整域降级为拒绝：`services/api/src/moderation/service.ts:398-402`
  > `if (deps.executionMode === 'real') return createFailClosedModerationService();`（`createFailClosedModerationService` 见 `:340`，各方法 `deny()` 见 `:353-359`）
- 配置侧只有「离线准备好的请求」，没有任何真实调用许可：`tools/ai-config.mjs:69`
  > `policySelectionVerified: key.startsWith('moderation') ? false : undefined, executionAllowed: false`
  以及 `:119` `mode: 'OFFLINE_PREPARED'`（endpoint/BizType 见 `:11-12`、请求体构造见 `:113-115`；**未读取任何凭据内容，只判有无**）。
- 结论：**不存在「硬规则兜底冒充 AI 审核」的隐瞒**——代码没有把规则层通过包装成模型结论；反过来说，**真实审核能力当前为 0 次外呼**，规则层命中/放行是唯一真实判定源。

### ② 失败时 fail-open 还是 fail-closed？——**答案：未发现 fail-open；装配、合流、发布、社区四层都是 fail-closed**

- 装配层：`services/api/src/moderation/provider.ts:109-113`（real 恒 fail-closed，且忽略调用方注入的替身）。
- 合流层：`services/api/src/moderation/service.ts:642-662`（`mergeModeration` 抛错 ⇒ `mergeFailed=['MODEL_PORT_ERROR']`），`:667-681`（每个 kind 投影 `decision:'quarantined', state:'uncertain'`）。
- 发布层：`services/api/src/moderation/service.ts:751-754`（撤回后 `TARGET_WITHDRAWN`）、`:758-761`（`REVISION_CONFLICT`）、`:769-777`（版本未知 `INPUT_UNCERTAIN`）、`:779-818`（逐 kind 双闸门 `isModelLayerPublishable` + `evaluateModelReReview`）、`:822-824`（才 `setVisibility(published)` + `setPublishedRevision`）、写后核对失败则 `:857-858` 补偿回写 `hidden` + 清空 published_revision。
- 社区层：`services/api/src/community/service.ts:864-868`（`gate.evaluate` 不过则先记拒绝判定再抛错）、`:874-877`（带媒体即使规则放行也不得发布）。
- 读面：`services/api/src/moderation/visibility.ts` 的 `VISIBILITY_REASON_CODES` 含 `RESCREEN_REQUIRED`（版本过期不得按「已审」返回），`service.ts:574` `versionFreshnessOf` 派生 stale。
- 证据强度：这是**读码 + 定向测试**，不是对真实供应商的失败注入（见 §7）。

### ③ 审核结论与发布是否同一事务/同一可见性判据？是否有「已发布后补审」窗口？——**答案：无该窗口，中间态是 private/pending**

- 先审后发的位置：`services/api/src/community/service.ts:862-863` 注释「先审后发：审核发生在任何内容行落库之前」；`:872-873` `screenWithModeration` + `requireDomainClearance`。
- 落库与结论**同一次原子提交**：`community/service.ts:993`（`const inserted = await store.insertPost(record, …)`：无媒体走 `buildVerdict`，带媒体走审核域的 `domainVerdict`）。
- 待审内容不是公开态：`community/service.ts:971` `awaitingPublish = !mediaReview && screen !== null && link !== null`；`:983-984` 待审落 `visibility:'private', audit_state:'pending'`（带媒体且媒体审核未过时同样落 private/pending）。
- 公开是独立的第二步，且失败只留私有：`community/service.ts:906-915`（`link.publish(...)`；闸门拒绝 ⇒ 行保留 private/pending，错误原样上抛）；发布侧写 `setVisibility(published)` 后才 `setPublishedRevision`，写后核对失败则补偿回写（`moderation/service.ts:822-824、补偿见 :857-858`）。
- 结论：**不存在「内容已公开、审核补在之后」的时间窗**；审核域与社区共享同一 `revision` 判据（旧版本结论会被 `REVISION_CONFLICT`/stale 挡掉）。
- 唯一不对称（设计取舍，非窗口）：real 模式下后台下架时可见性已置 `hidden`，随后 `withdraw()` 失败才 503（`app.ts:579-616`）——处置已生效但调用方看到错误，注释已声明重试不会自行恢复。
