## 2 实物

### 2.1 验收 1 前半：无授权与错用途不能触发实际外发

- **用途闭集与授权服务**：`services/api/src/privacy/consent-pg.ts` 的 `CONSENT_PURPOSES` 逐字 `['recording', 'media_processing', 'external_inference', 'public_posting']`；`createPostgresConsentService(pool, hmacKey, serviceOptions)` 返回 `{ grant, list, requireConsent, withdraw }`，`withdraw()` 在 `transaction()` 内按「account → session → epoch → record」顺序加锁（`SELECT ... FROM public.users WHERE id=$1::uuid FOR UPDATE`、会话 `FOR SHARE`、`auth_epoch` 比对），撤回成功即 `UPDATE public.privacy_epochs SET current_epoch=current_epoch+1, state='withdrawn'`——**epoch 前移使旧外发凭据失效**。

### 2.2 验收 1 后半：撤回／注销与任务竞争、旧结果回写

- **在途守卫**：`packages/privacy/in-flight.mjs` 的 `createInFlightGuard({ ledger, account, consentStore, now })`：
  - `assertAccountIntact`：`state !== 'active'` ⇒ `ACCOUNT_INACTIVE`；`auth_epoch` 不等于外发时冻结值 ⇒ `ACCOUNT_INACTIVE`「账号状态已变更，请重新登录」。
  - `assertAllConsentsIntact`：`isGranted` 为假 ⇒ `CONSENT_REQUIRED`「用途 ${purpose} 授权已撤回，禁止继续」；`currentEpoch !== epoch` ⇒ `OBJECT_UNAVAILABLE`「授权版本已变化，禁止继续」。
  - `assertVersionNotCancelled`：取消墓碑命中 ⇒ `OBJECT_UNAVAILABLE`「该对象版本已取消，回调不得复活」。
  - `assertExecutable({ exportId, userId })`：终态 ⇒ `OBJECT_UNAVAILABLE`。
  - `saveResult(...)`：保存前重查，且回调携带的 `objectVersion` 必须与外发预留时冻结的 `objectRevision` **完全一致**（旧版本回调写不到新版本上）。
- **撤回侧消费者**：`services/api/src/privacy/consent-pg.ts` 的 `EgressRevoker` 接口（`onConsentWithdrawn` / `onAccountSuspendedOrDeleted`，返回 `{ revokedInFlight: number }`）；`withdraw()` 在依赖存在时先探 `SELECT EXISTS(... public.media ...) OR EXISTS(... public.exports ...) OR EXISTS(... public.author_links ...) AS present`，存在且**未注入**撤销器 ⇒ `OBJECT_UNAVAILABLE`「已有资料或任务的撤回消费者尚未接入」（逐字注释「拒绝在途未撤销的部分撤回」），注入则 `await serviceOptions.egressRevoker.onConsentWithdrawn({ userId, purpose })`，抛错同样折叠成 `OBJECT_UNAVAILABLE`——**部分撤回被拒，不留半截**。`services/api/src/privacy/grant-pg.ts` 的 `persistConsentGrant(...)` 在授予侧有同形状守卫。
- **撤回器装配与可达性**：`services/api/src/app.ts` 里 `egressRevoker` 的表达式逐字是把 `privacyInjection?.egressRevoker` 优先，否则「`egressLedger === null || config.executionMode !== 'real'` ⇒ `undefined`，其余 `createEgressRevoker({ ledger: egressLedger })`」，注入 `registerConsentRoutes` 走条件展开。**撤回路径今天可达**（real + 有池）。
- **注销路径今天不可达（代码自认，逐字）**：`services/api/src/app.ts` 的注释「⚠ 可达性（实测）：本项注入门是「real ⇒ 有」，`available`（real ⇒ false）与之**互斥** ⇒ real 下 `requireWired()` 先 503、非 real 装配期不建撤销器 ⇒ **两条路都到不了这里**（仅 `privacyInjection` 测试注入可达）；要生效须先开放 real 注销，见 tests/unit/account-deletion-egress-revoker-reachability.test.mjs。」⇒ 注销触发的「撤销在途外发」**只有测试注入臂有证据**，生产形态没有。
- **注销受理仍整域 503**：`services/api/src/app.ts` 的 `createAccountDeletionRequestService({ ..., available: config.executionMode !== 'real' })`；`docs/architecture/contract-status.json` 的 `requestAccountDeletion` 条目 `status: "partial"`，blocker 逐字含「`real` 模式**仍整域 503 PROVIDER_UNAVAILABLE**（retryable:false）」。（2026-11-04 复核：本条已失效——`real` + 可用真库时受理开放（`services/api/src/app.ts` 的 `deletionAcceptanceDurable` 分支：`available: config.executionMode !== 'real' || deletionAcceptanceDurable`），POST 回 202、回执可读；唯一保留的 503 是 `real` 但**没有可用连接池**。契约台账同一 operation 的 blocker 也已按 GY-R74 改写成「不再整域关闭」，故上面引的「blocker 逐字含 real 整域 503」不再是今天的措辞。）

### 2.3 验收 2：日志脱敏 + 第三方删除「可追溯但不把请求当完成」

- **脱敏原语**：`packages/privacy/redact.mjs` 头注释「硬红线：日志严禁落私有正文、图片、音频、精确坐标、凭据」；敏感键含 `lat` / `lng` / `latitude` / `longitude` / `coordinates` / `coordinate` / `location`，值形态另判高精度坐标对（`^[-+]?\d{1,3}\.\d{5,}\s*[,;]\s*[-+]?\d{1,3}\.\d{5,}$`）、`data:` URI、长 base64、Bearer token ⇒ 一律 `[REDACTED]`；导出 `redactForLog(value, options)` 与 `assertNoSensitiveLeak(value, forbiddenFragments)`。写侧与派发器的日志只带 `request_id` / `recipient_id` / `reason`（见下条），不带正文。

FROM PUBLIC`（只授 EXECUTE）。头注释第 3 条把「**confirmed 一次写齐**」列为设计点，并指向 0003 第 8 节的 `third_party_confirmed_evidence` 约束（该句原文带行号，本页按纪律不复制行号，只保留约束名与节号）。

### 2.4 验收 3：前后端一致错误码与交互、模块删除注册协议、训练开关

- **前端契约**：`miniprogram/utils/consent-api.js` 头注释逐字列出三条调用（`listConsents GET /me/consents`、`grantConsent POST /me/consents`「Idempotency-Key 必填 8..128」、`withdrawConsent DELETE /me/consents/{purpose}`「Idempotency-Key + If-Match 必填」），并写「**服务端 `error.code` 原样透出**：`REVISION_REQUIRED`（428）、`REVISION_CONFLICT`（409）、`NOT_FOUND`（404）、`CONSENT_REQUIRED`（403）、`OBJECT_UNAVAILABLE`（409）……一律不改写成」。同一文件**自曝未取得**（逐字）：「未取得（如实标注）：微信编译器 / 真机未跑；本地 stub 下 `consent_policies` 没有可用行 ⇒ 授予大概率回 `403 CONSENT_REQUIRED`，本片证的是"按契约调用 + 失败如实呈现"，不是"真机授予/撤回链路已验"」。
- **服务端同口径**：`services/api/src/routes/consents.ts` 的 `registerConsentRoutes(app, config, pool, guards, testOptions)` 三条路由 + `GET /me/privacy-policy`（`onRequest: noStoreHook`）；授予与撤回都强制幂等键（`if (typeof key !== 'string' || key.length < 8 || key.length > 128) throw new ApiError('IDEMPOTENCY_KEY_REQUIRED', '缺少有效幂等键')`），撤回另强制版本前提（缺 `If-Match` ⇒ `REVISION_REQUIRED`；格式非法 ⇒ `INVALID_REQUEST`；CAS 失败 ⇒ `REVISION_CONFLICT`），成功回 `ETag: "<revision>"` + `Cache-Control: no-store`。
- **错误码闭集单一事实源**：`miniprogram/utils/states.js` 的 `CONSENT_REQUIRED: 'denied'`；`miniprogram/utils/auth.js` 逐字「契约 403 闭集（SCOPE_DENIED / CONSENT_REQUIRED / ACCOUNT_INACTIVE）」；`miniprogram/utils/identify-api.js` 把 `CONSENT_REQUIRED` 的 `retryAction` 定为 `grant_consent`，注释逐字「`grant_consent` 的按钮**不得**写成「去授权」…可授予的入口在 `pages/consent`」。
- **交互面**：`miniprogram/app.json` 的 `pages` 23 项含 `pages/consent/consent`；入口在 `miniprogram/pages/profile/profile.js` 的 `openConsent`（`wx.navigateTo({ url: '/pages/consent/consent' })`）；`miniprogram/pages/consent/consent.js` 只经 `consentApi` 调用，撤回后按用途给 `WITHDRAW_NOTES`（`external_inference` 逐字「撤回「外部推理」后：照片杂草识别、农药标签 OCR、语音问答、朗读合成外发会立刻全部被 403 CONSENT_REQUIRED 拒绝」），`grantAvailability(policy, purpose)` 决定某用途能否授予（无政策行 ⇒ 置灰并写原因）。
- **模块删除注册协议**：`packages/privacy/deletion-modules.mjs` 的 `createDeletionCoordinator({ registry, requiredModules, now })` 提供 `registerModule` / `registeredModules` / `DELETION_MODULE_LIMIT = 50`，只接受闭集内模块名（逐字「`registerModule` 只接受闭集内的模块名（未声明的模块注册即拒）」），缺模块按 `declared - registered` 报缺口；`packages/privacy/deletion.mjs` 的 `requestState()` 是无副作用只读取值器（查不到返回 `null`）。

### 2.5 「撤回后读面是否降级」——分两句话说，别混

- **用途授权撤回后，读面按设计不降级**。`services/api/src/routes/recognitions.ts` 文件头逐字：「**读取（GET）与删除（DELETE）不挂**：撤回用途后用户仍必须能取回并删除自己的数据。」`services/api/src/routes/media.ts` 同理：只有上传挂授权，GET／下载／删除／授权条目只 `guards.requireUser`。降级的是**外发/执行面**（`403 CONSENT_REQUIRED` / `SCOPE_DENIED`）。这是**有意为之**，不是漏挂。
- **会降级的读面确实存在，但触发条件是「内容授权/可见性/版本」，不是用途撤回**：`services/api/src/tts/service.ts` 的 `readAudio`（`GET /api/v1/speech/synthesis/{id}/audio` 的服务层入口）在取字节前调 `readAndDecide(row.checkedContentRef, row.ownerUserId, 'verify')`——注释逐字「来源可能下架、撤权、审核失效或 revision 变化，属主不能凭旧合成记录继续取回旧音频」「零字节拒绝：判定不通过时连 `readArtifact` 都不调用」；`verifyUsable` 用同一条判定。该判定走 `decideCheckedContent({ requested, callerUserId, snapshot })`，**只读内容核对快照，不读 `consent_policies`**。
- **「未找到」项（如实写）**：仓内**没有**「用途授权撤回后，该用途相关的 GET 读面一并降级/拒绝」的实现。若产品要「撤回后连历史都不给看」，今天不存在该行为，需要另行裁定（见 §6 第 5 条）。

## 5 判定

**判定：部分满足（维持 R74 的档位，但差额清单改写为下面三条）。**

理由：

1. **验收 2 的后半在可装配形态下不可达。** 条文要求「可追溯第三方删除请求／完成／失败」，而「完成」这一态需要真实接收方与 `evidence_ref` 签署方；仓内 `ThirdPartyDeletionRecipientSource` 只有接口声明，生产装配恒落 `RECIPIENTS_UNWIRED`，**零写**。写侧接通（#860）解决的是「有接收方之后能写对」，不解决「今天有没有接收方」。零写的证据不能反过来当「已完成」的证据。
2. **验收 1 后半的注销侧仍有不可达段。** 撤回侧 `egressRevoker` 今天可达（real + 有池），注销侧被 `available` 与注入门互斥卡死，仓内注释已自认，只有测试注入臂有证据；且 `real` 注销整域 503（`requestAccountDeletion` blocker 逐字）。条文写的是「撤回／注销与任务竞争…均被守卫阻断」，注销那一半今天在生产形态下没有可执行路径。（2026-11-04 复核：`available` 与注入门不再互斥——`services/api/src/app.ts` 按 `deletionAcceptanceDurable`（真库 + 受理可持久化）判定，real + 有池 ⇒ 注销受理可达；原句「real 注销整域 503」已不成立，只在 `real` 且无池时成立。）
3. **其余条文成立。** 验收 1 前半（无授权/错用途不外发）、验收 1 末（测试身份）、验收 2 前半（脱敏原语）、验收 3 三条（错误码一致、模块删除注册协议、训练开关关闭）都有仓内实物与实跑读数（§3.1、§3.2）。

为什么不是「未满足」：核心机制（用途授权、外发账本、在途守卫、撤回消费者、库层证据约束、前后端错误码闭集）都在仓内可用且被单测钉住，缺的是**外部条件**（真实接收方）+ **一条不可达的装配门**，不是「主体功能只到框架」。

为什么不是「已满足」：判断依据不是「证据够不够」（§11 已豁免读数要求），而是**条文里有两个状态在今天的可装配形态下根本产生不出来**——「第三方删除完成」与「注销触发的在途撤销」。

## 6 若改判「已满足」，剩下的边界是什么

1. **接收方来源与 `evidence_ref` 签署方仍是空白**：`ThirdPartyDeletionRecipientSource` 无实现，`evidence_ref` 由谁签（第三方回执单号／我方外发流水／签署的删除证明）未定。改判「已满足」等于承认「登记结构 + 写侧 + 证据约束」就够，`完成` 态的可达性不算条文——**这需要一次明确裁定，不是补代码**。
2. **`real` 注销仍整域 503**：`available: config.executionMode !== 'real'`，注销侧 `egressRevoker` 与 7 日/30 日执行链一起不可达；改判后这条边界要写成「注销侧撤销在途无生产证据」。（2026-11-04 复核：`available: config.executionMode !== 'real'` 是旧读法，今天判据是 `executionMode !== 'real' || deletionAcceptanceDurable`；真库臂 `tests/integration/account-deletion-pg.mjs` 已跑通 16 组。「注销侧撤销在途无生产证据」仍可保留，但理由不再是「整域 503」：real + 有外发台账时撤销器才装配，而受理可达后它随受理被调用（`tests/unit/account-deletion-egress-revoker-reachability.test.mjs` 的「可达性②／④」用例判撤销真的发生、调用一次且主体正确）；缺证据的是第三方完成态——`third_party_state: 'unsupported'`（`services/api/src/app.ts` 的 `thirdPartyWritable` 生产恒 `false`）。）
3. **真库臂：本页旧读数有误——写这一页时三支臂已经在 CI 里**：`tests/integration/third-party-deletion-pg.mjs`（2026-10-26 由 `#610`/`8b5b8afe` 接线，见 `.github/workflows/real-pg-integration.yml:259`）、`tests/integration/third-party-deletion-sql-pg.mjs`（2026-10-26 由 `#614`/`ed566893` 接线，见 `.github/workflows/real-pg-integration.yml:756`）、`tests/integration/egress-revoke-race-pg.mjs`（2026-10-22 由 `#421`/`906fe147` 接线，见 `.github/workflows/consent-grant-postgres.yml:66`）。本页当日把三支写成「都还没进 CI」，属当轮误判，不是后来才变化；「撤回竞态只有单测臂」的说法同样作废。（2026-11-09 订正：旧句按追溯保留在 §8 第 2 条，本条只按代码事实陈述。）
4. **没有真实第三方、没有真机、没有真实供应商**：一次真实外发、一份真实第三方回执都不存在；小程序授予/撤回链路未上真机。
5. **「撤回后读面不降级」是有意设计，不是遗漏**：`recognitions.ts` 与 `media.ts` 的注释都写明「撤回后用户仍必须能取回并删除自己的数据」。若产品口径要「撤回后连读也不给」，那是需求变更，不是把守卫补上。

7. **`[范围]` 第 4 条的「第三方删除请求接口」仍只有进程内形态**：库层函数 + 端口 + 回执投影，契约台账里没有对外 HTTP 操作。验收条文没写「对外」，但 `[范围]` 写了「接口」，改判时要把这层含糊写明。
