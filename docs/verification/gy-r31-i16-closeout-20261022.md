## 1. 事实核对（先读代码与 CI，不看台账）

### 1.1 `0018_favorites_history.sql` 建了哪四张表

`services/api/db/migrations/0018_favorites_history.sql`（单事务 `BEGIN; … COMMIT;`，纯新增）：

| 表 | 关键列 | 约束／索引 |
| --- | --- | --- |
| `favorites` | `id`、`owner_id`（外键→`users`）、`target_type`、`target_id`、`target_revision`、`revision`、`created_at` | 唯一索引 `favorites_owner_target_key(owner_id, target_type, target_id)`；分页索引 `favorites_owner_created_idx(owner_id, created_at DESC, id DESC)` |
| `history` | `id`、`owner_id`、`kind`（`recognition`/`ocr` 闭集）、`target_type`、`target_id`、`target_revision`、`revision`、`job_id`、`job_state`（7 项闭集）、`event_key`、`created_at` | 唯一索引 `history_owner_event_key(owner_id, event_key)`、`history_owner_target_key(owner_id, kind, target_id)`；分页索引 `history_owner_created_idx` |
| `favorites_idempotency` | `scope`、`key_hash`、`request_hash`、`response_status`、`outcome`（`NULL`=已认领未完成）、`expires_at` | 主键 `(scope, key_hash)`；过期扫描索引 `favorites_idempotency_expires_idx` |
| `history_idempotency` | 同构（`outcome` 的结果引用多一个 `cascade`） | 主键 `(scope, key_hash)`；`history_idempotency_expires_idx` |

三条与验收直接相关的建表决定（都写在迁移文件头的注释里，不是推断）：

- 去重**由数据库唯一约束裁决**，`INSERT … ON CONFLICT DO NOTHING` 命中即 `duplicate`，不靠「先查后写」；两域都是**物理删除**（无 `deleted_at`），因此「取消后再收藏得到新 id」由物理删除保证。
- `reference_state`（目标当前是否可得）**不入库**：每次读取重新派生，库里查不到这一列 —— 这是「下架／失效不因缓存或旧链接重新公开」的结构性前提。
- 注销清空 = `DELETE … WHERE owner_id = $1 RETURNING id`，以返回行数作证据。

回滚：`services/api/db/migrations/rollback/0018_favorites_history.down.sql`（纯新增 ⇒ 可整表 DROP，不触碰既有表）。

> 兼记一处**文件内过期注释**（只登记、本片不改）：该文件头写「三张表，一张都不多」，但紧接着列了 4 条、并确实建了 4 张表。数值以 4 为准。

### 1.2 `app.ts` 的装配行与门禁

`services/api/src/app.ts`（符号名即定位，不写行号）：

- 存储选择：`favoritesStore = favoritesInjection?.store ?? (config.executionMode === 'real' && pool !== null ? createPostgresFavoritesStore(pool, …) : createMemoryFavoritesStore(…))`；`historyStore` 同形，PG 臂是 `createPostgresHistoryStore`。相关 import 为 `services/api/src/favorites/store-pg.ts` 与 `services/api/src/history/store-pg.ts`。
- 服务层门禁（**唯一**开关）：`favoritesService = config.executionMode === 'real' && !favoritesStore.persistent ? null : createFavoritesService(…)`；`historyService` 同形。⇒ **只有 `real && !persistent` 才置 `null`**，路由侧 `null` 才回 503 `PROVIDER_UNAVAILABLE`。
- `persistent` 的真实取值：`services/api/src/favorites/store-pg.ts` 与 `services/api/src/history/store-pg.ts` 都声明 `persistent: true`；`services/api/src/favorites/store.ts` 与 `services/api/src/history/store.ts` 声明 `persistent: false`。⇒ `real` + 有 `DATABASE_URL`（`pool !== null`）时走 PG；无库时如实 503，**没有「内存冒充持久化」的路径**。
- 历史写入接线**只在非 `real` 成立**（本节据 2026-10-22 预审订正，原写「历史写入接线已存在」属过度声明）：`services/api/src/app.ts` 的端口选择判据仍是 `config.executionMode === 'real'` ⇒ `real` 取 `createUnwiredRecognitionTerminalHistoryPort` / `createUnwiredOcrTerminalHistoryPort`（传给它们的理由文案「real 模式：历史域为内存 store 整域关闭」已随迁移 0018 过时：`real` + 池时 `historyService` 已不再为 `null`）；`recordHistoryTerminal` → 内部创建口 `appendHistory`（确定性 `event_key`、同任务重复投递 no-op）只在**非 `real`** 分支生效 ⇒ **`real` + PG 生产路径不会写入 history 行**。
  - 真库臂 PASS 15/16 是**直接调** `app.historyService.appendHistory(…)` 的读数，**不覆盖** `recordTerminal → appendHistory` 这条接线；CI 的 `real-pg-17.11` step 也只跑该脚本。
  - 缺口属**代码侧**（把 `real` 的历史终态端口接到 `recordHistoryTerminal`，并订正上述过期注释）；本页 docs-only，不改代码，也不把该缺口记成已接线。台账同步：`listHistory` 已由工具重生成回 `partial`（§4）。
- 任务状态端口：`historyJobPort` 由 `createWiredHistoryJobPort` 装配，`resolve` 里按 `kind` 转调 `recognitionService.getJob` / `ocrService.getJob`（**读取时重查**，不吃入库值）。
- 可见性端口：`favoritesVisibility` / `historyVisibility` 默认取 `defaultVisibility`，即 `createWiredVisibilityPort` 的实例（#167 接线）。
- 级联仍然未接线：`historyCascadePort` 默认是 `createUnwiredHistoryCascadePort()`；`createWiredHistoryCascadePort` 在 `services/api/src/history/cascade.ts` 里**已存在但生产装配未调用**。这是 `deleteHistory` 保持 `partial` 的唯一理由。
