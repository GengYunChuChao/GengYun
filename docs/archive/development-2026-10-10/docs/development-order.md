## 1 怎么使用这个顺序

先核对最新 main、issue 领取评论、开放 PR 和当前 HEAD，再领取或继续已有工作。已合入的组件继续使用，不重新实现；新提交必须重新审查，旧 SHA 的结论不能套用到新 SHA。

下表是一种满足现有依赖的推荐序列，**不是必须关闭前一项才能开始下一项的单线程队列**。依据已审契约可并行编写、使用明确标注且隔离的替身联调；缺接入、授权、真实资料或样本时，记录待验证/依赖阻塞。组件合入不代表任务整项完成；真实业务验收仍须满足正式前置和该能力全部证据。

GY-I25 按微信身份、各 AI 能力、数据库、存储及真机分别登记接入事实。某项等待资源时，可推进其他已经具备开发条件的组件，不能将未验服务接入真实用户链路。单项接入成功也不能关闭 GY-I25 整项。

**第一条纵向链路：微信登录 → 有来源资料查询 → 确定性安全过滤 → 文字问答及引用检查。** 之后接普通话转写与播报，并推进识草、OCR 和真实社区。文字问答不等待完整 ASR，五 Tab 页面不等待 TTS。

## 3 并行方式与早期准备

每个任务仍核对机器台账中的全部正式依赖。以下并行是开发安排，不提前签整项验收，也不授权未验证能力上线。

| 条件/阶段 | 可以并行的工作 | 何时收口 |
| --- | --- | --- |
| M1 初始 | GY-I01 契约与 GY-I25 接入核查 | 契约审入；各接入项分别有证据 |
| 已审契约可用 | GY-I02 工程与 GY-I03 资料；GY-I20 可先采集、独立标注及整理来源 | 样本范围/来源稳定后冻结，调参前完成；数量与标准保持需求原值 |
| 工程组件可用 | GY-I27 授权基础与 GY-I26 页面 | 授权先于真实数据；页面按冻结契约联调并补界面实测 |
| 登录等各自前置具备 | GY-I06 媒体、GY-I05 档案、GY-I07 查询 | GY-I05 还须资料和页面前置；完成真实归属和来源验证 |
| 各能力前置满足 | GY-I09/10/11/12/13/14 可按接口分线；ASR 无须等待查询规则，文字问答无须等待 ASR | 各自真实接入与独立评估随能力 PR 提交；TTS 最终与检查后的真实回答联调 |
| 审核基础可用 | GY-I15 社区与 GY-I18 后台可分线；两类识别具备后 GY-I16 可独立推进 | 消息 GY-I17 在真实事件产生后联调；各任务其余依赖仍须满足 |
| 每个数据模块实现时 | 登记 GY-I19 删除处理器，准备 GY-I22 权限/失败反例，做 GY-I23 相应真机检查 | GY-I19/22/23 在表中末尾完成全量集成签核，不把首次测试留到比赛前 |

GY-I21 从 M1 准备，并持续消费每个能力的实测。GY-I20 的第 12 位是冻结验收位置，**不是采集启动时间**；GY-I21/22/23 的末尾位置是全量收口位置。

团队有多位实现者时，按上述分线安排；人员不足时使用推荐序列。有资源阻塞时推进其他具备条件的任务，同时记录输入负责人和预计交接时间，不让同一写手无限等待。建议每位实现者保持一个主要实施 PR，已有阻塞修订优先；不重复领取、重建分支或覆盖他人成果。

## 5 减少返修的提交方式

开工前从该 issue 的 F/AC 提炼可检查行为和证据，范围争议在提交前说明。每份 PR 尽量围绕一个可验证组件；部分交付使用 Refs，只有代码审入、正式依赖和整项证据齐全才使用 Closes。

PR/issue 记录以下字段，不预填“通过”：

- 任务 ID、真实 issue 编号、负责人、分支及 base/HEAD。
- 已合入组件、本次修改范围、剩余必交项和输入负责人。
- 正常/拒绝/取消/重复/过期/越权等与本次改动相关的检查；涉及任务时增加撤回、注销和旧回调反例。
- 验证命令与实际结果；普通 CI、微信工具、真机、供应商及数据库证据分别登记。
- 实测版本、样本/来源/规则 hash、失败样例和相应请求编号；原始媒体与凭据不入库。
- 开发替身、真实服务、来源种子、模拟资料和用户校正分别标识；不将替身或手改计入模型指标。
- 明确结论：组件待审/已审入、需修改、待验证或依赖阻塞；不把所有开放 issue 统一写成“未开始”。

界面证据记录实际窗口宽度、显示/字体档位、工具/客户端/基础库及所测代码版本，包含主要控件与必要的滚动末屏。系统显示放大、微信字体设置、静态 WXSS 核算、模拟器和双平台真机分开登记；不可用近似推算代替测量。代码需求中的微信字体适配仍属于初版要求。

供应商鉴权不等于真实能力达标；接入样例不等于全量独立评估；保存前的授权判断不等于实际保存处于同一原子边界。涉及这些路径的回归必须检查实际副作用和数据状态，不能只断言返回成功或报错。

## 6 协作与范围

用户自主命令指挥组织实施，协作者提交 PR，监工独立审查与批复。按用户 2026-10-04 指令，定时任务只审批、验证、GitHub 批复和通过后的合并，不自动联系、唤起或派发给指挥/写手。本建议的发布不构成重新分配任务或改变实际 GitHub 权限。

12 小时巡检保留；关键修订提交后可由用户即时触发审查。新提交、证据补充和 CI 状态变化分别登记，合并绑定实际已验 SHA，不绕过失败或未解决的阻塞。

首版仍包括真实识草/OCR、普通话语音问答/TTS、真实 AI 社区、收藏历史、应用内消息及独立后台。人工审核只留空入口；计划反馈、专家预警、合作与支付沙箱按二月规划。首版不启用用户训练；来源、权限、7/30 日删除、安全规则和需求第 6 节门槛保持原值。真实付费验证、生产部署或现实业务动作仍需对应明确授权。
