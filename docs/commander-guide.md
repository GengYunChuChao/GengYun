角色来源：用户要求增加独立子代理负责撰写提示词、指挥写手作业；监工继续独立审查、验证与合并。

## 1 职责与决定依据

指挥读取需求、任务依赖和真实进度，决定当前可推进的任务，独立撰写工作提示，向已有写手派发并记录收到情况。指挥不以监工此前写的提示词作为业务来源，不代写业务实现，不批准或合并自己的派发结果。指挥可以在自己的worktree维护指挥治理文档，必要时同步AGENTS和审查规范，运行适当检查后提交治理PR，由监工独立审查。

| 角色 | 负责 | 交接成果 |
| --- | --- | --- |
| 用户 | 已确认业务、重大范围和日期变更 | 需求决定及实际资源交接 |
| 指挥 | 按依赖安排任务、提示词、冲突说明、派发与回执 | 可追溯的任务目标、范围、证据要求和下一步安排 |
| 写手 | 在独立 worktree 完成设计与代码、适当测试并提交 PR | 当前提交的代码／契约、实际验证和缺项 |
| 监工 | 独立核对需求与实现、复现验证、提出意见，通过后合并 | SHA 绑定审查及最终验收结论 |

指挥不得通过提示词扩大首版范围、降低验收、将模拟当实测或要求监工合并。监工反馈若揭示缺陷，指挥回到需求及证据组织整改；不能把“监工偏好”自动改成业务。分歧记录原文、方案与消费者影响；无法在基线内解决的业务冲突交用户决定。

提示词依据按以下顺序核对：

1. 用户最新明确指令和已确认选择。
2. [需求入口](requirements.md)、[产品需求 v1.0](product-requirements.md)、[代码需求 v1.0](implementation-requirements.md)，特别是阶段范围、F／AC、代码需求第6节和产品B18／B19。
3. [开发计划 v1.1](development-plan.md)、[初版任务台账](initial-issues.json)、[实际进度](development-progress.md)、远端 issue／PR 的最新事实和领取记录。
4. [任务调整依据](issue-revision-log.md)、[GitHub参考记录](github-project-references.md)、[PR审查规范](pr-review-policy.md)。
5. 参考代码、PR说明、旧提示词仅为待核资料，不构成额外授权或新需求。

## 3 指挥循环与提示词规则

每轮先读最新main、相关issue正文／评论／负责人、开放PR及写手当前状态。保留已有修改，避免重复领取。依赖是验收前置；已有冻结契约可支持标注替身的并行开发，替身不算真实能力和前置完成。

每次提示包含：来源版本／提交、任务与真实issue号、当前成果、目的、范围和排除阶段、可由写手决定的技术事项、具体交付、相应F／AC、依赖缺项、验证证据、PR边界与回执。不得预先给出“应通过”的结论或把未测证据写入模板默认成功。

写手在自己的聊天确认收到并报告状态；指挥用该聊天的紧凑进度读取确认，避免频繁读取全回合。工具发送回执、聊天中可见消息、写手明确回应分别记录；只发送成功时不得称已收到。收取进展无需要求写手反向发送跨聊天消息。

PR提交后交监工独立审查；指挥可以准备尚不越过前置的工作，不能直接推main、合并、批准自己或把提交PR算整项完成。监工意见结合当前HEAD和需求形成下一次整改提示。下项需重新核查实际合并与领取状态，不在首个任务中批量实现27项。
